## 1. 과제 목적

IT융합대학 가운데에는 학생이 회의와 스터디에 쓰는 M-SPACE 방 5개가 있다. 학교가 예산을 들여 만든 공간이다. 그런데 평일 낮에도 비어 있는 때가 많다. 팀은 3주 동안 이 방에서 직접 개발하며 그 모습을 지켜봤다.

원인은 열쇠다. 지금은 학과실에 가서 명부를 쓰고, 학생증을 맡기고, 열쇠를 받아야 방을 쓸 수 있다. 학과실이 닫히는 18시 뒤와 주말에는 관리가 끊긴다. 교학팀에 문의한 결과 지금은 평일 하루 최대 8시간까지 대여할 수 있다.

IT융합대학 학생 15명에게 설문했다(10/13–11/6). 14명(93%)이 "방이 비었는지 직접 가 봐야 안다"를 가장 큰 불편으로 골랐다. 13명(87%)은 "학과실에 직접 가야 한다"를 골랐다. 15명 모두 지금 방식 대신 새 방식을 쓰고 싶다고 답했다(5점 만점에 전원 5점). 표본이 작아 방향 확인용으로만 썼다.

이 과제의 목적은 세 가지다.

1. 열쇠와 사람 없이 예약만으로 방을 열고 닫는다.
2. 학생이 말 한마디로 빈방을 찾고 예약하게 한다. 단, AI가 잘못 예약하는 일은 구조로 막는다.
3. 노쇼, 자동 퇴실, 두고 간 물건, 환기를 사람 대신 시스템이 처리한다.

## 2. 과제 내용

### 2.1 기존 방식과 대안의 문제, 우리의 해결

| 방식 | 문제 | 오디의 해결 |
| --- | --- | --- |
| 종이 명부와 열쇠 (지금) | 비었는지 가 봐야 안다. 18시 뒤와 주말에 못 연다. 학생증을 사람이 맡는다 | 폰에서 방 현황을 보고 예약, 문 앞 카메라에 QR을 비추면 입실 |
| 구글 폼·범용 예약 서비스 | 예약만 되고 출입, 노쇼, 실제 재실은 모른다 | 재실 센서로 노쇼와 자동 퇴실 판단, 방은 바로 다음 사람에게 |
| 무인 스터디카페 출입 솔루션 | 좌석·매장 단위이고 학교 계정과 이어지지 않는다 | 학교 메일 인증, 방 단위 규칙(30분 단위, 최대 2시간, 연장 1회) |
| 일반 AI 챗봇 예약 | 모델이 없는 방이나 틀린 시각으로 예약할 수 있다 | AI는 제안만 하고, 실행은 학생이 확인 카드에서 [확인]을 눌러야 한다 |

### 2.2 시스템 구성

【그림 1: 구성도. 학생 폰(웹앱) → 예약 서버(core) ← 오디 비서·MCP 서버 / 문 앞 QR 카메라 / 방 안 센서·카메라 / 판단 서버(사진 비교) / 관제 화면】

모든 기능은 예약 서버의 API로만 연다. 비서, QR 장치, 센서는 데이터베이스에 직접 붙지 않는다. 바깥 장치는 공통 인터페이스 뒤에 두어 가상 센서와 실제 센서, 클라우드 모델과 로컬 모델을 설정값 하나로 바꿔 끼운다.

| 영역 | 기술 |
| --- | --- |
| 예약 서버 | Java 21, Spring Boot 4, PostgreSQL, Flyway |
| AI 비서·MCP 서버 | Spring AI MCP 서버, Gemini 3.5 Flash Lite, Ollama 로컬 모델(비교용), Redis(대화 24시간), Open-Meteo 날씨, 광주 버스 도착 정보 |
| 화면 | React, Vite, TypeScript, PWA |
| 장치 | 문 앞 QR 카메라, PIR·조도·CO2 센서, 방 카메라, 판단 서버(시제품은 Jetson Orin Nano) |
| 배포 | Docker, GitHub Actions, GHCR, 학교 실습 서버 |

### 2.3 특장점과 수행 내용

**① 겹치지 않는 예약.** 같은 방 같은 시간의 겹침과 "대표자는 끝나지 않은 예약 1건"을 데이터베이스 제약으로 막았다. 코드에서 먼저 확인하는 방식은 두 요청이 동시에 통과할 수 있기 때문이다. 동시 요청 100건을 보내 중복이 0건임을 확인했다.

**② 믿을 수 있는 AI 비서 오디.** 학생이 "내일 수업 끝나고 2시간 빈방 잡아 줘"라고 말하면 오디가 시간표를 보고 빈방을 찾아 확인 카드를 띄운다. 빈방 찾기, 예약, 바로 쓰기, 연장, 취소, 퇴실, 시간표, 이번 주 계획, 날씨, 교내 셔틀, 시내버스 도착까지 도구 14개를 MCP 표준으로 열었다. 예약 같은 쓰기는 두 단계다. 확인 표는 한 번만 쓸 수 있고, 같은 확인을 두 번 보내도 예약은 한 건만 생긴다. 권한 검사는 예약 서버가 학생 본인 토큰으로 다시 한다. 학번과 전화번호는 외부 AI로 보내기 전에 가린다.

성능은 같은 시험지로 쟀다. 학생이 할 법한 질문 43개와 정답지를 만들고 코드 채점기로 점수를 매겼다. 판마다 한 가지만 바꿨다.

| 방식 | 점수 | 심각 오류 | 판단 |
| --- | --- | --- | --- |
| Gemini 3.5 Flash Lite, 처음 지시문 | 89.8 | 2.7건 | 기준 |
| Gemini 3.5 Flash Lite, 개선 지시문 | **98.5** | **0건** | 채택 (다른 키로 다시 재도 98.5) |
| 젯슨 로컬 qwen2.5:7b, 같은 지시문 | 32.3 | 1.0건 | 탈락 (예약 끝까지 성공 11.5%) |

심각 오류는 학생이 [확인]만 누르면 잘못된 예약이 실제로 생기는 실수다. 로컬 모델은 데이터가 학교 밖으로 나가지 않는 장점이 있어 측정했지만, 지금 크기로는 예약을 끝까지 해내지 못했다. 그래서 시연은 Gemini로 하고 로컬 모델은 같은 점수표로 계속 비교한다.

아침에 앱을 열면 오늘 수업, 내 예약, 날씨, 다음 교내 셔틀, IT융합대학 앞 1177 정류장 시내버스 도착을 카드 한 장으로 보여 주고, [듣기]를 누르면 읽어 준다. 셔틀은 학교가 공지한 시간표를 기준으로 한다. 브리핑은 모델을 거치지 않아 AI 사용 한도와 상관없이 나온다.

시간표 캡처를 올리면 "수업 끝나고"를 계산한다. 모델이 시각을 직접 읽으면 30분씩 밀려 65.4점이었다. 칸 끝을 픽셀로 재도록 바꾸자 100점이 됐다(합성 시간표 1장, 2회 측정).

**③ 두고 간 물건 알림.** 사람이 모두 나간 뒤 방 카메라가 한 번만 찍고, 그 사진을 빈 방 기준 사진과 비교한다. 사용 중에는 사진을 남기지 않는다. 물체 인식(YOLO), 사진 설명 모델(VLM), 두 사진 차이 비교를 학교 안 판단 서버 한 대에서 돌려 사진이 학교 밖으로 나가지 않는다. 시제품에서는 학교에서 받은 Jetson이 이 서버 역할을 한다. 판단은 퇴실 뒤 한 번, 사진 한 장에 약 3초라 몇 초 늦어도 학생에게 손해가 없다. 의자 위 가방을 놓치던 문제를 고쳐 정확도를 51%에서 89.7%로 올렸다【채울 칸 1: 수연, 방·물건 종류 수·시도 수】. ↳ 못 채우면: "팀 내부 시험 기준이다." 놓침과 오판이 함께 줄지 않아, 남의 물건을 잘못 보고 벌을 주는 일이 없도록 경고 없이 "방에 물건이 있어요" 알림만 보낸다. 사람이 찍힌 사진과 영상은 저장하지 않고, 사진은 30일 뒤 지운다.

**④ 무인 관제.** 관리자는 화면을 보기만 한다. 방 카드 5장에 인원, 입실, 퇴실, 공기 상태가 나온다. CO2가 오를 것을 미리 보고 공기청정기와 환기를 자동으로 켜고 끄며(시연은 화면에 상태가 나오는 가상 기기), 언제 어느 방에서 왜 켰는지 기록을 남긴다【채울 칸 2: 재웅, 예측 방식과 지표 한 문장】. ↳ 못 채우면: 이 괄호를 지운다. 환기가 필요하면 방 안 학생에게 바로 알린다. 1번 방은 실제 센서로 시험하고, 2–5번 방은 10월 21일부터 실습실에서 잰 실제 센서 기록으로 돌린 시뮬레이션이다. 예약 뒤 15분 안에 입실하지 않으면 노쇼로 풀고, 시간이 끝나면 자동 퇴실한다.

## 3. 활용 방안 및 기대효과

### 3.1 사업화 추진 전략 (실현가능성)

M-SPACE는 학교가 학생에게 무상으로 여는 공간이다. 그래서 학교에 오디는 수익 사업이 아니라 사람 없이 운영하는 도구다. 돈을 버는 사업화는 같은 키트를 다른 대학과 민간 무인 스터디룸·공유 회의실에 파는 쪽이다.

| 단계 | 할 일 | 남길 증거 |
| --- | --- | --- |
| 1. 교내 시범 | M-SPACE 1번 방 하나로 무상 시범운영. 장비는 팀이 가진 것을 쓴다 | 이용률, 노쇼율, 교학팀 처리 시간 전후 비교 |
| 2. 교내 확산 | 희망 단과대 세미나실에 같은 키트 설치 | 단과대별 이용률 |
| 3. 타 대학·민간 | 설치형 키트와 방 단위 구독 | 도입 사례 1곳 |

막힐 곳도 정해 두었다. 문을 개조하기 어려우면 기존 열쇠를 넣는 키박스형으로 시작한다. 잠금장치는 상용 제품을 쓰고 팀은 소프트웨어 연동을 맡는다. 학교가 외부 AI를 꺼리면 유료 등급(입력을 학습에 쓰지 않는 조건) 또는 학교 서버의 로컬 모델로 바꾼다. 관리 화면에서 공간을 한 번 등록하면 예약, 입실, 관제가 그대로 붙는다. 규칙 숫자도 코드가 아니라 설정값이다.

### 3.2 시장성

같은 문제, 곧 사람이 열쇠를 지키는 예약형 학습공간은 학과 세미나실과 스터디룸이 있는 대학 어디에나 있다【채울 칸 4: 영준, 교육통계서비스 4년제 대학 수와 출처】. ↳ 못 채우면: 이 괄호를 지운다. 학교 밖에서는 방 단위로 시간을 파는 무인 스터디룸이 같은 일을 사람이나 단순 출입기로 한다. 기존 대안은 예약만 되는 무료 서비스이거나 대규모 구축형 시스템이다. 오디는 방 단위로 무인 출입, 실제 이용률(재실 센서), 대화형 예약을 함께 준다. 방 안 카메라는 선택 기능이라 사진이 부담스러운 방은 끄고 쓸 수 있다.

비용 구조는 가볍다. 시중가로 계산한 방당 장비비는 약 44만 원이고, 그중 잠금장치가 30만 원이다. 방 카메라는 약 5만 원, 센서 보드와 PIR·조도·CO2 센서는 합쳐 4.5만 원이다. 판단은 방마다 하지 않고 학교 서버 한 대가 모아서 한다. 사진 한 장 판단에 약 3초라 방 100개가 하루 10번씩 써도 약 50분이면 끝난다. 방 5개 전체 도입비는 약 220만 원이다. 문을 바꾸기 어려운 방은 키박스형으로 더 줄인다. 서버는 학교 서버, AI는 무료 등급 또는 로컬 모델이라 운영비는 거의 들지 않는다.

| 항목 | 방당 금액 |

| 잠금장치(스마트 도어락) | 30만 원 |
| 방 안 카메라(선택) | 5만 원 |
| 센서 보드·PIR·조도·CO2 | 4.5만 원 |
| 문 앞 QR 카메라 | 3만 원 |

| 합계 | 약 44만 원 (5실 약 220만 원, 판단 서버는 학교 서버) |
