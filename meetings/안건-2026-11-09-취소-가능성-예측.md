> 기능 동결 11/13까지 **D-4**. 근거: 빈방 릴레이 Q-18 결정(요구사항 v0.4.29, docs #76), core `feat/relay`(core #101), core `develop` 47d4e09의 `reservation` 테이블.

## 0. 한 줄 요약

빈방 릴레이(기다리기)는 "취소되면 알려 준다"까지라 밋밋하다. 그 위에 **"기다릴 칸 3개 중 어디가 취소될 가능성이 높은지"를 정해진 규칙으로 계산해 등급(높음·보통·낮음)으로 보여 주고**, 비서는 "시도해 볼 만해요"라고 설명만 한다. 기다릴지는 학생이 정한다.

- 판단은 LLM이 아니라 **코드의 점수 공식**이 한다. 모델은 정해진 문장 틀에 등급과 칸을 넣어 말하기만 한다 (브리핑 #72와 같은 방식)
- 같은 기능의 반대편: 취소 가능성이 높은 예약의 **주인에게** 비서가 "이 예약 쓰실 거예요? 못 쓰면 놓아 주세요"라고 먼저 묻는다(Q-18에서 비서 몫으로 남겨 둔 "놓아줄까요?")

## 2. 기존 릴레이와 무엇이 다른가

| | 빈방 릴레이 (Q-18, 결정됨) | 취소 가능성 (이 안건) |
|---|---|---|
| 학생이 하는 일 | 차 있는 칸에 기다리기를 걸고 알림을 기다림 | **어느 칸에 걸지** 고를 때 등급을 보고 고름 |
| 풀어 주는 문제 | 취소된 자리를 먼저 기다린 사람에게 공정하게 넘김 | 기다리기가 1인 **3개**로 제한돼서, 아무 칸에나 걸면 허탕 |
| 시스템이 하는 일 | 줄 순서 관리, 5분 잡아 두기 | 칸마다 취소 가능성 점수 → 등급 |
| AI(비서)의 몫 | 없음 (화면 버튼) | "이 칸이 시도해 볼 만해요" 설명, 예약 주인에게 "놓아줄까요?" |
| 발표에서 보여 줄 것 | 기다리면 알림이 온다 | **예측이 실제 취소와 얼마나 맞았는지 숫자** (6장) |

> 왜 3개 제한이 중요한가: 기다리기를 무제한으로 걸 수 있으면 다 걸면 되니 예측이 필요 없다. 3개라서 "어디에 걸까"가 진짜 선택이 된다.

## 3. 먼저 짚을 전제 두 가지 (영준 아이디어에서 바뀌는 부분)

### 3-1. "평균 30분만 쓰고 금방 빠질 사람"은 취소가 아니라 **조기 퇴실**이에요

- core 규칙상 취소는 **시작 전**에만 된다(FR-RSV-007). 릴레이는 그중에서도 **시작 30분 전까지** 취소된 자리만 넘긴다
- "다음 수업이 3시라 금방 빠질 것"은 사용 중 퇴실이라 **릴레이가 넘기지 않는다**. 퇴실하면 그냥 빈 칸이 되고 먼저 본 사람이 잡는다
- 그래서 평균 이용 시간은 취소 점수에 넣지 않고, 따로 "곧 빌 것 같은 방" 힌트(방 현황 `room_status`)에 쓰는 게 맞다. 조기 퇴실도 기다리던 사람에게 넘기려면 릴레이 규칙을 바꿔야 한다(동결 뒤)

### 3-2. 다른 사람 시간표는 **기다리는 사람 쪽에 쓰면 안 돼요**

- 비서는 **요청한 학생 본인의 토큰**으로만 일한다(비서 안전 규칙). 시간표는 비서 Redis에 학생별로 있어, 예약 주인의 시간표를 기다리는 학생의 요청에서 읽으려면 서비스 공용 권한이 필요하다 → 규칙 위반
- 대신 **예약 주인 본인에게** 쓰면 문제가 없다: 주인이 앱을 열면 브리핑이 "이 예약이 3시 수업 바로 앞이에요. 못 쓰면 놓아 주세요 [취소]"라고 묻는다. 주인의 토큰·주인의 시간표·주인의 결정이다
- 결과적으로 기다리는 사람은 시간표를 보지 않고도 "취소가 더 일찍 나오는" 효과를 얻는다

## 4. 기준과 점수 공식 (초안)

**예측하는 것:** 이 예약이 **시작 30분 전까지 취소될** 확률 (릴레이가 넘겨 줄 수 있는 사건만)

### 4-1. 기준 후보

| 기준 | 데이터 출처 | 개인 정보인가 | 동결 전 |
|---|---|---|---|
| ① 칸 기본 취소율: 같은 요일·시간대 미리 예약이 취소된 비율 | core `reservation` (status, start_at) | 아니오 (집계) | 가능 |
| ② 미리 잡은 정도: 예약한 때(`created_at`)부터 시작까지 간격 | core `reservation` | 아니오 (그 예약의 속성) | 가능 |
| ③ 예약 주인의 지난 취소율 (최근 30일) | core `reservation` (owner_id, canceled_at) | **예** | 회의 결정 (5장) |
| ④ 예약 주인의 시간표와 겹침 | 비서 Redis 시간표 | **예** | 기다리는 쪽 X, 주인 쪽 넛지만 |
| ⑤ 비서로 만든 예약인지 (`created_via`) | core | 아니오 | 효과 모름, 뺌 |
| ✕ 평균 이용 시간 | core (checked_in_at, checked_out_at) | 예 | 취소 점수에서 뺌 (3-1) |

### 4-2. 공식 (숫자는 모두 설정값, 측정 뒤 조정)

```
b   = 칸 기본 취소율 (기준 ①). 기록이 30건 안 되면 설정값 0.15 (추정 시작값)
r   = (주인 취소 수 + k·b) / (주인 미리 예약 수 + k),  k = 5      ← 기준 ③, 쓰지 않으면 r = b
L   = 미리 잡은 정도 배수 (기준 ②): 3일 이상 ×1.3 · 1–3일 ×1.0 · 하루 안 ×0.6
p   = min(0.9, r × L)

등급: p ≥ 0.35 높음 · 0.15 ≤ p < 0.35 보통 · p < 0.15 낮음
표시 안 함: 시작 30분 전 이후, 사용 중(IN_USE), 내가 들어 있는 예약
```

- `k`(평활 상수)의 뜻: 예약 2번 중 1번 취소한 사람을 "50%"로 보지 않고, 기록이 쌓일 때까지 평균(b) 쪽으로 당긴다. 기록이 적은 사람에게 낙인을 찍지 않는 장치
- 함께 보여 줄 것: **내 줄 순서**. 등급이 높아도 내가 4번째면 앞 사람이 받아 간다. 화면은 "가능성 높음 · 내 순서 1번"처럼 둘을 같이

### 4-3. 대안과 비교

| 방법 | 장점 | 약점 | 판단 |
|---|---|---|---|
| **규칙 점수 (위 공식)** | 왜 그런지 설명 가능, 데이터 적어도 동작, 테스트 쉬움 | 계수가 감(추정) | **추천** |
| 로지스틱 회귀 | 계수를 데이터로 맞춤 | 학습할 실제 데이터가 없음(5개 방·테스트 계정) | 동결 뒤, 데이터 쌓이면 |
| LLM에게 판단시키기 | 만들기 쉬움 | 같은 입력에 답이 바뀜, 근거 검증 불가, 개인 기록이 Gemini로 나감, 하루 500회 한도 | **안 함** |

### 4-4. 콜드 스타트 (기록이 없을 때)

| 상황 | 처리 |
|---|---|
| 처음 쓰는 학생 (주인 기록 0건) | `r = b` (평균으로 봄). 개인 기록이 점수를 바꾸지 않음 |
| 시스템 전체 기록이 적음 (칸 기록 30건 미만) | `b` = 설정값 0.15, 화면에 "아직 기록이 적어 대략이에요" |
| 시연 | 6장의 모의 데이터를 넣은 dev DB로 |

## 5. 개인정보

| 쟁점 | 위험 | 제안 |
|---|---|---|
| 취소 이력(③)을 다른 학생 안내에 씀 | 처리방침 1장 목적(예약·출입·노쇼·신고)에 없는 **목적 외 이용**. 예약 주인을 아는 친구는 등급으로 "저 사람 취소 잘함"을 추론 | 회의에서 A/B 중 고름. A: ③을 빼고 ①②만(개인 정보 0). B: ③을 넣되 처리방침에 목적 추가(P-7) + 동의 체크 |
| 숫자 노출 | "62%" 같은 숫자는 근거를 캐묻게 하고, 틀리면 신뢰가 무너짐 | **등급 3단계만**. 숫자·주인·이력은 화면·비서 답에 안 나옴 |
| 근거 문구 | "예약한 사람이 자주 취소해요"는 개인 이력 공개 | 근거는 칸 기준 일반 문구만: "이 시간대는 취소가 잦은 편", "며칠 전에 잡힌 예약" |
| 시간표(④) | 남의 시간표를 기다리는 사람 쪽에 쓰면 노출 + 비서 토큰 규칙 위반 | **주인 본인 넛지에만** (3-2). 주인이 시간표를 넣은 경우만 |
| 외부 AI(Gemini) | 이력 숫자가 프롬프트에 들어가면 밖으로 나감 | 모델에는 칸·등급·내 순서만. 문장은 코드 틀 |
| 낙인·불공정 | 등급 높은 칸에 기다리기가 몰리면 주인이 압박을 느낌 | 주인에게는 "기다리는 사람 수"를 보여 주지 않음(회의 질문) |

## 6. 맞았는지 검증하는 방법

**기록:** 학생이 등급을 처음 본 순간을 남긴다. 새 테이블 `relay_prediction (id, reservation_id, predicted_at, p, grade, version)` (새 Flyway 번호). 예약 시작 시각이 지나면 결과(시작 30분 전까지 `CANCELED`였나)를 붙인다.

**숫자 3개:**

| 지표 | 뜻 | "맞았다"의 기준 (안) |
|---|---|---|
| 등급별 실제 취소율 | 높음·보통·낮음 등급에서 실제로 취소된 비율 | 높음 > 보통 > 낮음 순서가 지켜짐 |
| Brier 점수 | (예측 확률 − 실제 0/1)²의 평균. 낮을수록 좋음 | "모두 평균값 b로 예측"보다 낮음 |
| 높음 등급 적중 | 높음이라 한 예약 중 실제 취소 비율 | b의 2배 이상 |

**시연용 데이터 (실제 운영 데이터는 11/20 전에 거의 없음):**
- 가짜 학생 200명 × 4주 예약을 만든다. 학생마다 숨은 취소 성향을 정해 두고(대부분 낮고 일부 높게), 미리 잡을수록 취소가 잦게 뽑는다
- 앞 3주로 점수를 내고 4주차로 맞혀 본다 → 등급별 실제 취소율 막대 그래프 1장
- 발표에서는 **"모의 데이터 검증"이라고 분명히** 말하고, 실제 정확도는 운영 데이터가 쌓여야 안다고 적는다

**일부러 망가뜨려 볼 실험**
1. 모든 가짜 학생의 취소 성향을 똑같이 만든다 → 점수가 "평균값 예측"보다 나아지면 안 됨(나아지면 공식이 잡음을 외운 것)
2. `k = 0`으로 바꾼다 → 예약 1번·취소 1번인 학생이 바로 "높음"이 되는지 보고, 평활이 왜 필요한지 확인

## 7. 필요한 core API·데이터와 비서 도구

### 7-1. core (지영)

`GET /api/relay/chances?date=2026-11-12` — 로그인 필요, 그날 **차 있는 칸**의 등급

```json
[{ "roomId": 1, "startAt": "2026-11-12T14:00:00+09:00", "endAt": "2026-11-12T16:00:00+09:00",
   "grade": "HIGH", "reasons": ["SLOT_OFTEN_CANCELED", "BOOKED_EARLY"], "waiting": 2 }]
```

- `grade`: `HIGH`·`MID`·`LOW`. `reasons`는 칸 기준 코드만(개인 이력 코드 없음). `waiting`은 그 칸에 줄 선 사람 수
- 내가 들어 있는 예약, 시작 30분 전 이후 칸은 빠짐
- 오류: `400 INVALID_REQUEST`(날짜 형식), `400 RESERVATION_OUT_OF_RANGE`(7일 밖)
- 짚을 것
  - **트랜잭션:** 읽기 전용. `relay_prediction` 기록이 실패해도 조회는 성공해야 하므로 기록은 따로(별도 트랜잭션, 실패는 로그만)
  - **동시성:** 상태를 바꾸지 않아 잠금 없음. 등급을 본 뒤 기다리기를 거는 사이에 칸이 바뀌어도 기다리기 API(core #101)가 다시 확인하므로 문제없음
  - **인덱스:** 주인 이력(③)을 쓰면 `reservation (owner_id, created_at)` 인덱스 추가. 지금은 `owner_id` 인덱스가 끝나지 않은 예약용 부분 인덱스(`one_active_per_owner`)뿐이라 지난 기록 조회는 전체 훑기
  - **트래픽(시험 기간):** 하루 칸 수는 5방 × 48칸이 최대라 계산은 작음. 칸 기본 취소율(①)은 하루 한 번 계산해 캐시, 날짜별 결과는 1분 캐시

### 7-2. 비서 (영준)

| 도구 | 종류 | 하는 일 |
|---|---|---|
| `relay_chances(date)` | 읽기 | 위 API를 부르고, 코드가 "가능성 × 내 순서"로 상위 3칸을 골라 문장 틀로 답함: "14–16시 1번 방은 시도해 볼 만해요(가능성 높음, 지금 2명 대기). 기다릴지는 직접 정해 주세요" |
| `relay_wait(roomId, startAt)` | **쓰기 (두 단계 확인)** | 확인 카드 → [확인]에서 `POST /api/relay/waits`. 쓰기 규칙대로 확인 토큰 1회용 |
| 브리핑 넛지 | (도구 아님) | 내 예약이 내 시간표 수업 직전·직후로 빠듯하면 "못 쓰면 놓아 주세요 [취소]". core 변경 없음, 이미 있는 `my_reservations`·`my_schedule`로 |

- 예약 주인 정보(이름·학번)는 비서가 받지도, 모델에 넣지도 않는다

| **B. 개인 정보 없이 (추천)** | core API(①②만) + 예측 기록 + 비서 `relay_chances` + 넛지 + 모의 검증 | ③ 넣기(동의 뒤), `relay_wait` 도구, 조기 퇴실 넘기기 | core 0.5일, 비서 0.5–1일, 검증 0.5일 |
| C. 발표 서사만 | 넛지(비서 단독) + 모의 데이터 검증 그래프 | 기능 전부 | 비서 0.5일 |

- **B를 추천하는 이유:** 처리방침을 고치지 않아도 되고(①②는 개인 정보가 아님), core 일이 반나절이라 core #98·#101 등 열린 일과 겹쳐도 들어갈 여지가 있다. ③이 없어도 "예측 → 실제 비교" 서사는 그대로 선다
- 공통 전제: **core #101(릴레이)이 먼저 머지**. 안 되면 자동으로 C
