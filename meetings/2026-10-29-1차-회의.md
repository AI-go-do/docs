## 한눈에

회의의 결론은 “**키 문제만 풀면 나머지 문제가 거의 다 풀린다**”였다. 키를 교학팀에서 받고 돌려주는 방식 때문에 17–18시 이후 사용과 시험 기간 24시간 개방이 제대로 굴러가지 않는다.

**회의에서 정한 것**

- 중복 예약은 **DB와 서버 둘 다에서** 막는다.
- 관리자 승인 대신, 도서관처럼 **반납 버튼을 누르면 바로 반납**되게 바꾼다.
- 예약 시간이 끝나면 **자동 반납**한다.
- 센서 기능은 기본 데모만 만들고, 학과가 원하면 추후에 더한다고 발표한다.
- 다음 회의에서 설문 결과와 개인정보 방침을 본다.

**아직 정할 것**

- 같은 사람이 하루에 몇 번까지 예약할 수 있나
- 출입 방식: 기존 키 / 키패드 OTP / QR + 전자석 잠금 / OTP 키박스
- 재실 감지 센서: 이산화탄소 / 열감지 / 기타
- 반납 안 하고 나간 사람에게 경고를 줄지, 얼마나 줄지
- 조기 반납으로 빈 시간을 30분 단위로 자를지, 유연하게 할지

아래에서 각 주제마다 **팀 의견**과 **Claude 의견**을 나눠 적었다. Claude 의견은 제안이고, 결정은 팀이 한다.

## 현재 운영 방식과 공간 구조

현관 안내문 기준으로, 지금 M.Space는 **예약이 안 되고 교학팀에 직접 가서 키를 받는** 방식이다.

**현재 방식의 문제 (회의에서 나온 것)**

- 17–18시에 교학팀이 퇴근하면 키를 받거나 돌려줄 수 없다.
- 시험 기간 24시간 개방 때는 키 없이 열어 둔다. 가방만 두고 나가도 아무도 제재할 수 없다.
- 지금 빈 방인지 미리 알 방법이 없다.
- 불을 켜 두고 나가는 일이 잦다.

**주의:** 안내문에 “예약 불가”가 규칙으로 적혀 있다. 예약 시스템을 도입하려면 교학팀이 이 규칙을 바꿔야 한다. 기획안에 "운영 규칙 변경 필요"를 분명히 적어야 한다.

## 논의 주제별 정리

### 1. 같은 사람의 중복 예약

**팀 의견**

- 대표자 이름만 바꿔 여러 번 예약하는 걸 막으려면 신청 인원을 DB에 넣어야 한다.
- DB와 서버에서 이중으로 막는다. "오늘 이미 예약함"을 true/false 값으로 두고 트리거를 거는 안이 나왔다.
- 반론: 한 명이 서로 다른 두 팀(예: Java 팀, Python 팀) 회의에 모두 들어가야 할 수 있다. 하루 1회로 막으면 정직한 팀이 못 쓴다.

**Claude 의견**

- **"하루 1회" 대신 "같은 사람이 같은 시간에 두 방에 있을 수 없다"를 막는 게 맞다.** 두 팀 회의에 차례로 들어가는 건 허용하고, 시간이 겹치는 것만 막는다.
- 독점을 막을 다른 규칙은 **대표자 기준 하루 총 시간 상한**(예: 4시간, 설문으로 조정)과 **동시에 잡을 수 있는 예약 1건**이면 충분하다.
- true/false 플래그는 자정에 초기화, 취소와 반납 처리가 꼬이기 쉽다. 플래그를 따로 두지 말고 예약 행 자체에 제약을 거는 게 안전하다. 동시에 두 요청이 들어와도 DB가 하나만 통과시킨다.

```sql
-- PostgreSQL: 같은 방, 같은 시간 겹침 금지 (취소·반납된 예약은 제외)
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE reservation ADD CONSTRAINT no_room_overlap
  EXCLUDE USING gist (room_id WITH =, tstzrange(start_at, end_at) WITH &&)
  WHERE (status IN ('BOOKED','IN_USE'));
-- 참가자 테이블에도 같은 방식으로 (member_id, 시간 범위) 겹침 금지
```

### 2. 대리 예약과 실물 확인

**팀 의견**

- 지금은 교학팀에서 실물 학생증을 보여 주고 키를 받는다. 예약만 온라인으로 바꾸면 개선되는 건 "예약 현황 보기" 뿐이다.
- 중앙도서관 개인 캐럴은 예약 후 QR을 찍으면 영수증에 난수 번호가 나오고, 방 앞 키패드에 입력해야 들어간다. 시간 안에 안 오면 노쇼로 잡힌다. 이 방식을 가져오면 좋겠다.
- 키를 쓰는 이유는 예약한 본인이 실제로 와야 받을 수 있어서다. 친구가 대신 예약하는 걸 막는 역할이다.

**Claude 의견**

- 예약 번호를 본인 계정으로만 받게 하면 대리 예약은 상당 부분 줄어든다. 친구에게 번호를 알려주는 것까지 막을 수는 없다. 도서관도 같다.
- 완벽하게 막는 것보다 **원래 교학팀 방식(학생증 대조)보다 나빠지지 않은가**를 기준으로 삼자. 발표에서도 그렇게 답하면 된다.

### 3. 출입 방식과 24시간 운영

**팀 의견**

- 시험 기간은 24시간 개방인데 교학팀은 18시에 퇴근해서 키 반납이 불가능하다. 키만 해결하면 기존 문제가 거의 다 사라진다.
- 후보: 아두이노 키패드 + 난수 번호, OTP 도어락, QR 리더 + 전자석 잠금(EM락), ESP32·RFID, 문짝은 두고 키 박스만 디지털로.
- 문짝을 바꾸는 건 부담이 크다. 키 박스는 트레이드오프가 있다.
- 재료비 10만 원 지원이 통과되면 방 하나에 시범 설치해 볼 수 있다. 실제로 한 방에서 테스트까지 하면 강력하다.
- 학교가 "왜 돈을 써가며 바꾸냐"고 할 수 있다. 우리 비용으로 하면 문제없다는 의견.

**Claude 의견**

- **MVP는 OTP 키박스를 권한다.** 기존 열쇠를 그대로 쓰고, 방 앞에 작은 보관함을 달아 앱에서 받은 번호로 열게 한다. 문짝을 건드리지 않아 시설 승인 부담이 가장 작고, 방에 돌아가지 않은 키도 감지할 수 있다.
- 문에 전자석·도어락을 다는 건 학교 시설팀·소방 규정(비상시 문 열림) 확인이 필요하다. 일정 안에 승인이 나기 어렵다(확인 필요).
- 대회 데모는 책상 위 모형(ESP32 + 키패드 + 작은 잠금장치)으로 충분하다. 실제 방 설치는 승인되면 하는 2단계로 둔다.
- 학교 설득 포인트는 비용이 아니라 **교학팀 업무가 줄고, 18시 이후와 시험 기간에도 관리가 된다**는 점이다.

### 4. 재실 감지 (노쇼, 자리 비움, 불 켜 두고 퇴실)

**팀 의견**

- 카메라로 사람을 찍는 건 개인정보 문제가 있고 사람들도 불편해한다. 이산화탄소 센서로 재실을 보면 카메라가 필요 없다.
- 단, 이산화탄소는 값이 천천히 바뀐다. 30분은 지나야 조금 변한다. 열감지도 후보다.
- 예약하고 밥 먹으러 가서 비워 두는 문제, 불 켜 두고 나가는 문제도 센서로 관리자에게 알릴 수 있다.
- 센서는 기본 데모만 만들고, 학과가 원하면 추후 추가한다고 발표한다.

**Claude 의견**

- 이산화탄소만으로는 **15분 노쇼 판정을 못 한다.** 팀이 말한 대로 반응이 너무 느리다.
- \*\*적외선 동작 센서(PIR)\*\*는 가만히 앉아 있는 사람을 놓친다. **밀리미터파 레이더 재실 센서**(예: LD2410 계열)는 숨쉬는 정도의 움직임도 잡아 정지한 사람을 감지하고, 영상이 없어 개인정보 문제도 없다. 가격도 낮은 편이다(추정).
- 제안 조합: **레이더(사람 있음/없음) + 조도 센서(불 켜짐) + 이산화탄소(환기 알림·이용 추세)**. "빈 방인데 불 켜짐"이 한 번에 잡힌다.
- 센서 값만 보고 바로 제재하면 오판이 생긴다. 센서는 **알림과 자동 반납 판단의 근거**로만 쓰고, 제재는 누적 경고로 간다.

### 5. 반납과 시간 단위

**팀 의견**

- 2시간 예약하고 30분 만에 끝나면 남은 1시간 반이 낭비된다. 반납 버튼이 필요하다.
- 지금은 시작 후 취소도 반납도 안 돼서, 일찍 나가면 노쇼까지 되는 문제가 있다.
- 반납 안 하고 나가면 경고를 주자(3회, 5회 누적 등). 단, 사용자에게 압박이 될 수 있는 트레이드오프가 있다.
- 17:01에 반납해도 30분 단위라 17:30까지 29분이 남는다. 도서관처럼 반납하면 바로 다음 사람이 예약할 수 있게, 시작 시간을 유연하게 하자.

**Claude 의견**

- **예약은 30분 단위로 두되, 지금 빈 방은 "바로 사용"으로 즉시 시작**할 수 있게 하자. 다음 예약 전까지 남은 시간만큼 쓴다. 미리 잡는 예약은 정리되고, 빈 시간은 낭비되지 않는다.
- 상태를 분명히 정의하자: 예약됨 → (15분 안 체크인) 사용 중 → 반납 또는 시간 종료 자동 반납. 체크인이 없으면 노쇼. 상태 변경은 "현재 상태가 맞을 때만" 바꾸는 조건부 UPDATE로 해야 반납과 자동 반납이 동시에 일어나도 꼬이지 않는다.
- 반납 안 누른 사람: 재실 센서가 10분 이상 비어 있다고 보면 자동 반납하고 **알림만** 보낸다. 같은 일이 한 달에 3번 쌓이면 경고를 준다. 압박은 줄이고 낭비는 막는 절충안이다.
- 노쇼 기준 15분은 "조금 빡세다"는 의견이 있었다. 설문에 넣어 10/15/20분 중 고르게 하자.

### 6. 본인 인증과 학교 DB 연동

**팀 의견**

- 도서관처럼 학교 학생 DB와 연동하면 좋겠지만, 개인정보라 학교가 허락하지 않을 것 같다.
- 학교 개선 사항이라 잘 설명하면 될 수도 있다. 한 번 물어보자.

**Claude 의견**

- 학교 DB 연동은 이번 일정 안에는 어렵다고 보고, 우선 **학교 메일(@chosun.ac.kr) 인증**으로 가자. 학교 구성원인지는 확인되고, 우리가 학생 명부를 들고 있지 않아도 된다.
- DB 연동은 "학교가 원하면 붙일 수 있다"는 다음 단계로 발표한다.

### 7. 데모 초기화 버튼

- 데모 초기화 버튼을 누르면 노쇼 기록을 피할 수 있다. 시범운영 전에 **관리자만 쓸 수 있게 하거나 없애야 한다** (Claude 의견).
- 시험 기간 "키 없이 시작" 모드도 가방만 두고 24시간 차지할 수 있어 고쳐야 한다는 것이 팀 의견이다. 시험 기간에도 같은 예약·체크인 규칙을 적용하면 된다.

## 출입 방식 비용 비교

대회용으로는 **DIY 모형(추정 3–5만 원)**, 실제 시범 설치는 **OTP 키박스**가 현실적이다. 가격은 모두 추정이거나 회의 중 검색한 값이라 구매 전에 다시 확인해야 한다.

| 방식 | 비용 (방 1개) | 문 개조 | 24시간 운영 | 대리 예약 방지 | 메모 |
| --- | --- | --- | --- | --- | --- |
| 지금 방식 (교학팀 열쇠) | 0원 | 없음 | 불가 | 학생증 대조 | 18시 이후 반납 불가 |
| DIY 모형 (ESP32 + 키패드 + 작은 잠금장치) | 3–5만 원 (추정) | 없음 (책상 위 데모) | 데모로 시연 | 본인 계정 번호 | 대회 발표용 |
| OTP 키박스 (기존 열쇠 보관) | 10–30만 원 (추정) | 없음 (벽 부착) | 가능 | 본인 계정 번호 | 시설 승인 부담 가장 작음 |
| OTP 도어락 | 20–40만 원 (회의 중 검색) | 있음 | 가능 | 본인 계정 번호 | 시설팀 승인 필요 |
| QR 리더 + 전자석 잠금(EM락) | 수십만 원 이상 (회의 중 검색, 확인 필요) | 있음 | 가능 | QR 본인 확인 | 배선·전원·소방 규정 확인 필요 |

**재실 감지 센서 (방 1개, 추정)**

| 센서 | 하는 일 | 비용 | 한계 |
| --- | --- | --- | --- |
| 밀리미터파 레이더 (LD2410 계열) | 사람 있음/없음, 가만히 앉아 있어도 감지 | 수천 원대 | 감지 범위 조정 필요 |
| 적외선 동작 센서 (PIR) | 움직임 감지 | 수천 원대 | 정지한 사람을 놓침 |
| 조도 센서 | 불 켜짐 감지 | 수천 원대 | 창문 햇빛과 구분 필요 |
| 이산화탄소 센서 | 환기 알림, 이용 추세 | 수만 원대 | 반응이 느려 노쇼 판정 불가 |

재료비 지원은 나오지 않아 **전부 사비**다. 그래서 대회용은 갖고 있는 아두이노 키트로 DIY 모형만 만들고, 상용 키박스·도어락은 학교가 시범운영을 확정한 뒤에 검토한다. 실행 계획은 아래 「돈 안 쓰는 실행 계획」에 있다.

## 대회 관점에서 본 약점과 보완 (Claude 의견)

IT Festival 캐스톤 심사는 1차 40점이 명확성/창의성이고, "모든 내용을 객관적으로 입증"해야 한다(2025 기준). 이 기준으로 보면 약점은 다섯 가지다.

| 약점 | 왜 문제인가 | 보완 |
| --- | --- | --- |
| 공간 예약은 흔하다 | "예약 사이트"로만 보이면 창의성 점수가 낮다 | 차별점을 3개로 좁힌다: 키 없는 24시간 무인 운영, 재실 기반 자동 반납, 예약률이 아닌 실제 이용률 |
| Jetson이 꼭 필요한가 | 키패드·센서는 ESP32만으로도 된다 | Jetson은 층 단위 허브: 여러 방 센서를 모아 재실을 판정하고, 이용률 보고서를 학교 밖으로 데이터를 보내지 않고 로컬 AI로 만든다. IT Festival 자체는 Jetson을 요구하지 않는다(공고 기준) |
| 설문 표본이 작다 | 응답 6–7명으로는 "학생 요구가 많다"를 입증하기 약하다 | 2차 회의 전까지 에브리타임·학과 단톡방으로 더 모으기 (목표 30명 이상) |
| 현재 규칙은 "예약 불가" | 교학팀이 규칙을 바꿔 주지 않으면 시범운영이 불가능하다 | 기획안에 규칙 변경안을 넣고 교학팀과 협의 |
| 실제 사용 데이터가 늦게 나옴 | 희망 시범운영은 12/7–12/24, 대회 마감은 11월 말(작년 기준) | 팀·지인 소규모 테스트로 1주일치 기록 남기기, 시범운영 앞당기기 요청 |

**역할 분담도 미리 정해야 한다.** 과제설명서에 참여도(%)를 적어야 한다. 기존 예약 서버는 영준이 1인으로 만든 부분이라, 팀원 몹을 눈에 보이게 나누는 게 좋다. 예: 출입 모형(ESP32·키패드), 재실 센서와 판정, 이용률 분석·AI 보고서, 반납·노쇼 로직과 화면.

**개인정보도 있다.** 카메라를 빼도 "누가 언제 어느 방을 썼는지" 기록은 개인정보다. 수집 항목, 보관 기간, 이용률 보고서는 개인을 빼고 방 단위로만 만든다는 원칙을 2차 회의에서 정하자.

## 돈 안 쓰는 실행 계획

지원금 없이 전부 사비로 한다. 아두이노 키트가 많아서 **새로 살 것은 레이더 재실 센서 1개(수천 원대, 추정) 정도**다. ESP32가 키트에 없으면 1개를 더해도 합계 2만 원 안쪽이다(추정).

| 필요한 것 | 쓰는 것 | 비용 |
| --- | --- | --- |
| 키박스 모형 | 아두이노 4×4 키패드 + 서보모터 걸쇠, 상자는 종이 또는 3D프린터 공작실 출력(사용 조건 확인 필요) | 0원 |
| 재실 감지 | 키트의 PIR·초음파 센서. 가만히 앉은 사람까지 잡으려면 레이더 센서 추가 | 0원 / 수천 원 |
| 불 켜 둠 감지 | 키트의 조도 센서(CdS) | 0원 |
| 이산화탄소 | 수업 때 쓰던 센서·데이터 재활용 | 0원 |
| 정답(라벨) 기록 | 구글 시트에 입·퇴실 시각 기록. 필요하면 테스트 중에만 동의를 받고 C920 + Jetson으로 사람 수 기록 (제품에는 카메라 없음) | 0원 |
| 서버 | 이미 만든 예약 서버 + 노트북 또는 학교 서버 | 0원 |

Jetson은 **보드 B만** 쓴다. 보드 A는 팀원의 시계열 수집기가 돌고 있어 건드리지 않는다.

### 테스트 장소: 3번 방

3번 방은 창문 수리로 사용 불가라 예약 충돌 없이 실험하기 좋다. 단, 학교 시설이라 **교학팀 허락이 먼저**다. 수리 중에는 작업자 출입과 창문 개방으로 값이 흔들릴 수 있고, 수리가 끝나면 다시 일반 이용으로 돌아간다. 수리 종료일을 같이 확인한다.

교학팀에 보낼 문장 예: “3번 방이 수리로 비어 있는 동안, 붙였다 뗄 수 있는 센서와 작은 상자를 두고 테스트해도 될까요? 영상 촬영은 하지 않습니다.”

### 실제 사용자 없이 하는 테스트

정확도 측정은 실제 사용자보다 **팀원이 정해진 동작을 하는 연출 테스트가 더 좋다.** 정답을 우리가 정확히 알기 때문이다. 시나리오마다 10번 반복하면 "70번 중 몇 번 맞음"이라는 발표용 숫자가 나온다.

| 시나리오 | 동작 | 맞혀야 할 것 |
| --- | --- | --- |
| 빈 방 | 아무도 없이 몇 시간 켜 두기 | 계속 "없음" (에어컨·커튼·햇빛 오탐 확인) |
| 기본 입·퇴실 | 들어가서 10분 있다 나감 | 있음 → 없음 시각 |
| 가만히 앉기 | 30분 동안 노트북만 보기 | 계속 "있음" (PIR이 가장 많이 틀리는 경우) |
| 짐만 두고 나감 | 가방 두고 20분 뒤 복귀 | 그동안 "없음" |
| 노쇼 | 예약만 하고 안 들어감 | 15분 뒤 노쇼 |
| 일찍 끝남 | 2시간 예약, 30분 만에 나감, 반납 안 누름 | 빈 방 감지 → 자동 반납 |
| 불 켜고 퇴실 | 불을 켜 둔 채 나감 | 관리자 알림 |
| 복도 통과 | 문 앞을 지나가기만 함 | "없음" 유지 |
| 키박스 | 맞는 번호·틀린 번호·만료된 번호, 와이파이 끈긴 상태 | 열림·거부, 인터넷 없이도 검증 |

실제 사용자가 꼭 필요한 건 **실제 이용률, 노쇼 비율, 반납 버튼을 실제로 누르는지** 같은 행동 데이터다. 이건 시범운영에서 모은다.

### 시험 기간 기록

시험 기간 24시간 개방은 **관리 없이 그냥 열어 둔다.** 누가 몇 시간 쓰는지, 가방만 두고 자리를 차지하는지 아무도 모른다. 이번 시험 기간에 몇 번 둘러보고 "방 5개 중 몇 개가 사람 없이 짐만 있었다"를 기록하면 설문보다 강한 증거가 된다. 사진은 사람이 나오지 않게 찍는다.

## 교수님 2차 피드백: 확장성 있는 설계

핵심은 “**장비나 데이터가 없으면 설계로 푼다**”이다. 최소 기능을 먼저 배포해 눈에 보이게 만들고, 인터페이스와 어댑터로 기능을 하나씩 끼워 넣는다.

- **최소 기능 먼저:** OTP 같은 기능은 처음에 만들지 말 것. 예약을 먼저 배포하고 살을 붙인다.
- **감지는 인터페이스로:** "감지한다"를 추상화하고 카메라·레이더·CO2는 구현체로 둔다. "레이더가 없어서 카메라로 했지만 어댑터만 끼우면 된다"고 발표에서 말할 수 있다. UI에서 감지 방식을 고를 수도 있다.
- **출입도 어댑터로:** 중요한 건 "누가 출입했다, 문이 열렸다"는 사실이다. OTP 키패드, RFID 카드, 핸드폰 블루투스는 각각 어댑터다. 지금은 열쇠로 구현하고 프로토콜만 설계해 둔다.
- **학교 데이터도 어댑터로:** 학교는 데이터를 안 줄 것이다. 우리 내부 형식(시간표, 공지)을 정해 두고, JSON이든 XML이든 학과 홈페이지 스크래핑이든 변환기를 끼운다. 학과마다 형식이 달라도 저장은 똑같은 형태로 한다.
- **AI는 MCP + 나만의 비서:** 예약·일정·공지 기능을 MCP 도구로 만들고, 비서 에이전트가 도구를 골라 쓴다(오케스트레이션). "4명이서 스터디 예약해 줘", "이번 주 행사 있어?", "이 과목 휴강이래". 처음엔 채팅(텔레그램 봇 등), 음성은 나중, 멀티 에이전트는 확장 단계다.
- **모델은 갈아 끼울 수 있게:** 테스트는 Gemini API로 충분하고, Jetson의 Ollama 로컬 모델이나 GPT로 바꿀 수 있게 설계한다.
- **CO2는 환기 알림:** 좋은 방이라 농도가 오르면 졸음이 온다. 일정 수준을 넘으면 "10분 환기" 알림을 준다.
- **학생 인증:** 학교 메일로 코드를 보내 확인하고, 가입한 학생 정보는 수정할 수 없게 막는다.
- **협업 방식:** ORG에 기능 단위로 저장소를 나눠 충돌을 피한다. 기능 하나를 같이 만들면 경계를 잘못 잡아 충돌이 많아진다. API 스펙과 공통 규칙을 정하고, 팀원의 API 문서를 AI에게 주면 연동해 준다. 만들고 보니 MSA가 되는 흐름.
- **역할 예시:** IoT·센서 / 프론트 / 데이터 수집 / MCP 서버.
- **공부할 것:** AI가 제안한 구조가 무슨 디자인 패턴인지(파사드, 어댑터 등) "왜 이렇게 했나"를 이해한다. MCP와 함수 호출(function calling)도 공부한다.
- **오픈소스:** MIT, Apache 2.0 등 라이선스를 확인하고 밝힌 뒤 쓴다.

## 확장성 설계안 (Claude 제안)

제안하는 구조는 **포트와 어댑터 구조**(헥사고널 아키텍처)다. 예약·출입·재실 같은 핵심 규칙은 인터페이스(포트)만 알고, 센서·문 장치·학교 데이터·AI 모델·알림 채널은 바깥에 끼우는 어댑터로 둔다. 교수님이 말한 "어댑터를 끼워 넣는 설계"를 구조 전체에 적용한 것이다.

> 그림(확장성 설계 · 서비스 4개와 포트)은 Claude 문서 원본에만 있습니다. 구조 요약은 [TEAM.md](../../TEAM.md) 5장.

웹 화면은 게이트웨이로 예약 코어를 바로 부르고, 채팅은 비서 에이전트가 MCP 도구를 거쳐 같은 API를 부른다. 장치가 바뀌어도 점선 상자 안의 어댑터만 바뀐다.

### 포트(인터페이스)와 어댑터

| 포트 | 지금 만들 어댑터 | 나중에 끼울 어댑터 | 패턴 |
| --- | --- | --- | --- |
| `PresenceDetector` (재실 감지) | 아두이노 PIR, 수동 체크인 | 레이더, 카메라(Jetson), CO2 | 전략(Strategy) |
| `AccessDevice` (출입 장치) | 열쇠 대여(관리자가 버튼으로 기록) | 키패드 OTP, RFID, 블루투스 | 어댑터 |
| `AcademicDataSource` (학사 정보) | 직접 입력·CSV | 학과 홈페이지 스크래퍼(학과별), 학교 API(JSON/XML) | 어댑터 |
| `LlmClient` (AI 모델) | Gemini API | Jetson Ollama, GPT | 전략 |
| `NotificationChannel` (알림) | 웹 알림·이메일 | 텔레그램, 카카오 | 전략 |
| `IdentityVerifier` (학생 인증) | 학교 메일 코드 | 학생증 사진 확인, 학교 로그인 연동 | 전략 |

핵심은 **모든 어댑터가 같은 내부 형식으로 바꿔서 넘긴다**는 점이다. 출입 장치가 무엇이든 서버에 들어오는 건 `AccessEvent` 하나다.

```java
// 포트: 핵심 코드는 이 인터페이스만 알고, 장치가 무엇인지 모른다
public interface PresenceDetector {
    PresenceReading read(long roomId);
    String source();            // "PIR", "RADAR", "CAMERA" ... UI에서 선택
}
public record PresenceReading(long roomId, Instant at, boolean present, double confidence, String source) {}

// 출입: 장치별 프로토콜은 어댑터가 번역하고, 서버에는 이 이벤트만 들어온다
public record AccessEvent(String eventId, long roomId, String deviceId,
                          AccessType type, String credentialRef, Instant at) {}
public enum AccessType { OPENED, CLOSED, DENIED }

// 새 장치 = 새 클래스 하나. 기존 코드는 안 고친다
@Component
class PirPresenceAdapter implements PresenceDetector { /* ESP32가 보낸 값 읽기 */ }
```

### 왜 이렇게 설계하나

- **장비가 없어도 지금 돌아간다.** 수동 체크인, 열쇠 대여도 같은 포트의 어댑터라, 나중에 장치가 생겨도 핵심 코드를 안 고친다.
- **발표 질문에 답할 수 있다.** "레이더는 없어서 PIR로 했고, 어댑터 하나만 추가하면 된다."
- **AI가 기존 코드를 안 건드린다.** "이 포트의 새 어댑터를 만들어"라고 하면 클래스 하나만 늘어난다. 구조가 없으면 AI는 전체를 다시 짠다.
- **테스트가 쉽다.** 가짜(fake) 어댑터로 연출 테스트 시나리오를 코드로 돌릴 수 있다.

**대안과 비교**

| 방식 | 장점 | 문제 |
| --- | --- | --- |
| 한 서비스에 if문 분기 | 처음에 가장 빠름 | 장치·데이터가 추가될 때마다 핵심 코드를 고침. 4명이 같은 파일을 건드려 충돌 |
| 처음부터 서비스 7–8개 MSA | 경계가 분명 | 3주 안에 배포·연동·장애 대응 부담이 큼 |
| **포트·어댑터 + 서비스 4개 (제안)** | 확장은 어댑터로, 충돌은 저장소 분리로 막음 | 서비스 간 데이터 일관성을 따로 챙겨야 함 |

교수님은 MSA를 권하셨다. 다만 서비스가 많아질수록 "예약 확정과 출입 번호 발급이 다른 서비스에서 따로 일어나는" 문제가 생긴다. 그래서 처음엔 **4개**로 시작하고, 필요할 때 나누는 걸 권한다.

### 서비스 4개와 담당

| 서비스 (저장소) | 하는 일 | 담당 예시 |
| --- | --- | --- |
| 예약 코어 | 회원·학교 메일 인증, 예약·반납·노쇼, 출입 번호 발급 | 영준 (기존 코드) |
| 디바이스·센서 | ESP32·센서 값 수집, 재실 판정, 출입 이벤트, CO2 환기 알림 | IoT·센서 담당 |
| 학사 정보 수집 | 학과 공지 스크래퍼(학과별 어댑터), 시간표·행사 내부 형식 저장 | 데이터 수집 담당 |
| 비서 에이전트 + MCP | MCP 서버(도구), 비서 에이전트, 텔레그램 봇, 모델 교체 | MCP 담당 |

프론트(웹 화면)는 예약 코어와 함께 가거나, 팀에서 한 명이 따로 맡는다. 앞단에는 API 게이트웨이(nginx 또는 Spring Cloud Gateway) 하나를 둔다.

### MCP 도구 목록 (초안)

| MCP 서버 | 도구 | 하는 일 |
| --- | --- | --- |
| 예약 | `find_available_rooms` | 시간·인원으로 빈 방 찾기 |
| 예약 | `create_reservation` / `cancel_reservation` / `return_room` | 예약·취소·반납 |
| 예약 | `my_reservations` | 내 예약 보기 |
| 예약 | `room_status` | 재실·CO2 현황 |
| 학사 | `list_notices` | 학과·기간별 공지 |
| 학사 | `class_changes` | 휴강·보강·강의실 변경 |
| 학사 | `my_schedule` | 내 일정·과제(직접 등록한 것) |

**안전장치 (백엔드 관점)**

- AI를 믿지 않는다. MCP 도구는 로그인한 사용자의 토큰으로 호출하고, "남의 예약을 취소하지 못한다" 같은 권한 검사는 예약 코어가 한다.
- 예약·취소처럼 무언가를 바꾸는 도구는 실행 전에 "3시 창작실 2, 4명으로 예약할까요?"라고 확인을 받는다.
- 두 사람이 비서로 동시에 같은 방을 예약해도 DB 제약이 하나만 통과시킨다. 비서는 실패를 받으면 다른 시간을 다시 제안한다.
- 서비스 사이는 분산 트랜잭션을 쓰지 않는다. 예약 코어가 "예약 확정" 이벤트를 같은 트랜잭션에서 기록(outbox)하고, 받는 쪽은 같은 이벤트가 두 번 와도 한 번만 처리(eventId 중복 방지)한다.
- Jetson의 작은 로컬 모델은 도구 고르기 정확도가 Gemini보다 낮을 수 있다(확인 필요). 그래서 데모는 Gemini로 하고, "모델만 바꿔 로컬에서도 돈다"를 보여 주는 정도가 안전하다.

### 3주 마일스톤 (제안)

| 주차 | 목표 | 끝났다는 기준 |
| --- | --- | --- |
| 1주차 | 요구사항·ERD·API 공통 규칙 확정, 예약 최소 기능 배포(예약·반납·메일 인증), 포트 인터페이스와 가짜 어댑터 | 팀원이 폰으로 예약하고 반납할 수 있음 |
| 2주차 | 예약 MCP 도구 + 비서(텔레그램 채팅, Gemini), PIR 어댑터, CO2 환기 알림 | 채팅으로 예약이 됨, 센서 값이 화면에 보임 |
| 3주차 | 학과 공지 스크래퍼 1–2개, 모델 교체(Ollama) 시연, 연출 테스트 정확도 측정, 발표 자료 | "이번 주 공지 알려 줘"가 동작, 정확도 숫자 확보 |

**약점:** 비서와 MCP를 붙이면 AI 점수는 오르지만 범위가 빠르게 커진다. 매주 "끝났다는 기준"을 넘지 못하면 다음 주 기능을 더하지 말고 그 주 것부터 완성한다. 또 학과 홈페이지 스크래핑은 사이트 이용약관과 요청 빈도를 확인하고 한다.
