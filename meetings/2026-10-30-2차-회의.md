# M-SPACE 2차 팀 회의 정리

Oct 30, 2026 · @나영준

## 한눈에

2차 회의(10/30)에서는 설문 결과를 보고, 1차 회의 때 남겨 둔 안건을 정했다. 설문에서 나온 불편은 우리가 예상한 것과 같았다. 빈 방인지 가 봐야 알고, 학과실이 닫히면 반납을 못 한다.

- **예약 규칙:** 7일 전부터 예약, 1회 최대 2시간, 대표자는 끝나지 않은 예약 1건만, 빈 방은 바로 사용·연장, 노쇼 15분
- **기능:** 키 없는 24시간 운영(대회·2단계 목표. 학교 시범운영은 키 지급 유지), 학교 이메일 인증, 신고, 사진 체크인·체크아웃(선택)
- **하드웨어:** 아두이노 키패드를 MVP로, 실제 도어락·QR은 인터페이스만. 키박스는 제외. 재실 센서는 레이더 + 조도 + CO2
- **운영:** 서비스 하나를 한 명이 처음부터 끝까지 맡고, 매일 아침 스크럼에서 각자 슬라이드 4장으로 발표
- **테스트 장소:** 1층 모의 환경
- **팀 이름:** AI-go-do (11/2 확정, NoKey에서 변경. 학교 제출 자료에서는 서비스 이름 M-SPACE를 앞세운다)

## 설문 결과

응답자는 6명 정도로 표본이 작다. 수연님이 카톡방에 홍보해 응답을 더 모은 뒤 다시 계산한다.

| 가장 불편한 점 | 비어 있는지 가 봐야 알 수 있음 |

설문에서 나온 불편은 모두 우리가 예상한 것이었다. 표본이 작아 의견이 갈린 항목은 다수 의견에 집중하기로 했다.

**10/30 설문 수정:** Q5를 새 규칙(2시간 / 대표자 1건 / 7일)으로 바꾸고, Q10을 "비품 고장 + 무단 사용 신고"로 넓혔다. Q12 학교 이메일 인증, Q13 사진 체크인, Q14 AI 비서를 추가했다(자유 의견은 Q15). 기존 응답 6건의 Q5는 옛 규칙(3시간 / 하루 1건)에 대한 답이라, Q5는 10/30 이후 응답만 따로 집계한다.

## 예약 규칙

| 규칙 | 내용 |
| --- | --- |
| 예약 가능 범위 | 오늘부터 7일. 달력에 7일만 표시하고 날짜·시간을 고름 |
| 1회 예약 | 최대 2시간 |
| 대표자 | 끝나지 않은 예약을 **동시에 1건만**. 끝나거나 반납하면 다음 예약 가능 |
| 참여자 | 제한 없음. 단 같은 시간에 두 방은 금지 |
| 반납 | 반납 버튼을 누르면 즉시 반납. 관리자 승인 없음 |
| 자동 반납 | 예약 시간이 끝나면 자동 반납 |
| 빈 방 바로 사용·연장 | 다음 예약이 없으면 허용. 도서관처럼 끝나고 비어 있으면 다시 예약해 계속 사용 |
| 노쇼 | 시작 후 15분 안에 체크인이 없으면 노쇼 |

**왜 "하루 시간 한도" 대신 "대표자 동시 1건"인가:** 회의에서는 하루 1건, 하루 시간 한도(토큰), 끝나면 다시 예약 세 가지가 나왔다. 하루 1건은 두 팀 회의에 들어가야 하는 사람을 막고, 시간 한도를 참여자까지 깎으면 한도가 30분 남은 팀원 때문에 팀 전체가 못 쓴다. 독점은 미래 예약을 쌓아 둬 때 생기므로, "대표자 동시 1건"이면 그걸 직접 막고 하루 한도는 따로 필요 없다. 월·화·수 회의가 필요하면 팀원 3명이 한 건씩 대표자가 된다. 3명이면 하루에 몰아도 최대 연속 6시간으로, 회의에서 괜찮다고 본 수준이다.

```sql
-- 대표자당 끝나지 않은 예약 1건: 동시에 두 요청이 와도 DB가 하나만 통과시킴
CREATE UNIQUE INDEX one_active_per_owner
  ON reservation (owner_id) WHERE status IN ('BOOKED', 'IN_USE');
```

**7일을 둔 이유:** 특별한 근거는 없고 "주간 회의를 한 번에 잡을 수 있는 길이"다. 설문은 3일/14일로 반반 갈렸다. 대표자 동시 1건 규칙이 있으면 기간을 늘려도 독점 위험은 크지 않다. 다만 먼 날짜 예약일수록 노쇼가 늘 수 있어(추정) 7일로 시작하고, 시범운영 노쇼 비율을 보고 조정한다.

## 역할 분담

모두 취업 준비 중이라 이 프로젝트가 각자의 포트폴리오·이력서가 된다. 그래서 공평의 기준은 일의 양이 아니라 **면접에서 30분 동안 깊게 설명할 수 있는 기술 문제를 한 명당 하나씩 갖는 것**이다. 확장성 설계에서 나눈 **서비스 4개를 한 명씩 맡아 API·화면·테스트까지 끝까지 만든다.** 프론트 담당은 따로 두지 않는다.

| 사람 | 맡는 서비스 (API + 화면 + 테스트) | 면접에서 깊게 설명할 문제 | 결과로 보여 줄 숫자 |
| --- | --- | --- | --- |
| 영준 | 비서 에이전트 + MCP 서버 (+ 학사 정보 수집기) | LLM을 믿지 않는 구조: 권한 검증은 예약 코어에서, 쓰기 작업은 사용자 확인 후 실행, AI 모델을 갈아 끼우는 어댑터 | 작업 성공률, 잘못된 쓰기 시도를 막은 비율 |
| 지영 | 예약 규칙 v2 + 신고·노쇼 (내 예약 화면, 사진 체크인·체크아웃 포함) | 동시 예약 경쟁 상태 해결: 시간 겹침 차단 제약, 대표자당 1건 부분 유니크 인덱스, 연장·즉시 반납 처리 | 동시 요청 100건에서 중복 예약 0건 |
| 수연 | 디바이스·센서 서비스 (방 현황 화면 포함) | 같은 신호가 두 번 와도 한 번만 처리(eventId 중복 제거), 센서 값 저장 구조, 재실 판정 로직, 키패드 연동 | 재실 판정 정확도, 초당 처리 건수 |
| 재웅 | 인프라 + 인증 | 게이트웨이, 무중단 배포, AWS 비밀값 관리(OIDC), 학교 이메일 인증, 부하 테스트 | 초당 처리량과 응답 시간 |

- **예약 코어를 지영님에게 맡기는 이유:** 영준은 v1을 혼자 만들어 이미 이력서에 쓸 경험이 있다. 가장 백엔드다운 문제(동시성·인덱스·트랜잭션)를 다른 팀원에게 넘기고, 기존 코드를 아는 영준이 PR 리뷰를 맡는다. 지영님이 부담스러우면 재웅님과 맞바꾼다(재웅: 예약 규칙 / 지영: 인증 + 부하 테스트).
- 팀에 IoT 경험자가 없다. 첫 주는 "센서 값 하나를 서버로 보내기"까지만 목표로 하고, 아두이노 키트를 가진 영준이 같이 시작한다.
- ESP32는 아두이노 키트 6개 중 1개뿐이다.
- AWS 키와 비밀값은 저장소에 올리지 않고 GitHub Actions Secrets에만 넣는다. AWS 예산 알림부터 켜 둔다.
- 기여도는 PR로 남는다. 한 사람이 코드를 다 잡으면 충돌은 없지만, 다른 팀원은 질의응답·면접에서 설명할 게 없다. 그래서 기능 단위로 나눈다.

* **수연님이 서버 쪽까지 맡는 이유:** 아두이노만 하면 백엔드 이력서와 연결이 약하다. 센서 값을 받아 저장하고 판정하는 서비스까지 맡아야 할 이야기가 생긴다.
* **재웅님에게 부하 테스트를 붙인 이유:** 인프라는 결과를 숫자로 보이기 어렵다. 부하 테스트가 "초당 몇 건" 한 줄을 만든다.
* **학사 정보 수집기:** 비서가 쓰는 데이터라 영준에게 붙였다. 일정이 밀리면 가장 먼저 뺀다.

**잡일은 돌아가며**

- 스크럼 마스터: 주 단위로 돌아가며 맡는다. 한 명이 계속하면 그 사람의 구현 시간이 깎인다.
- 화면 공통 틀: 첫날 AI로 같이 잡고 끝낸다. 특정 한 사람의 역할로 두지 않는다.
- 문서: 각자 자기 서비스 문서를 쓴다. 재웅님은 전체 목차와 기술 스택 문서만 맡는다.
- 발표 영상(5분): 한 명당 자기 서비스 시연 1분. 과제설명서 참여도는 25%씩, PR·리뷰 기록으로 뒷받침한다.

**한 명당 반드시 남길 것**

1. 끝까지 맡은 서비스 하나 (PR 기록으로 증명)
2. 트러블슈팅 기록 2건 이상 (스크럼 슬라이드 2번 장이 그대로 쌓인다)
3. 결과 숫자 하나
4. 발표 영상에서 자기 시연 1분

## 매일 스크럼 운영

아침 스크럼에서 각자 **슬라이드 3–4장**으로 자기 작업을 발표한다. 이 슬라이드가 쌓이면 최종 발표 자료와 면접 포트폴리오가 된다.

| 시간 | 할 일 |
| --- | --- |
| 아침 스크럼 (20분) | 1인 4분, 슬라이드 4장 |
| –15:00 | 구현 (AI 활용). 15시에 PR 올리기 |
| 15:00–퇴근 | 오늘 코드 읽기, 결정 기록·트러블슈팅 기록, 다른 팀원 PR 리뷰, 내일 슬라이드 준비 |

**슬라이드 4장 양식 (고정)**

1. 어제 한 것 (화면이나 PR 링크)
2. 트러블슈팅: 무엇이 안 됐고, 원인은 무엇이고, 어떻게 고쳤나
3. 왜 이렇게 결정했나 (다른 선택지와 비교)
4. 오늘 할 것, 새로 제안하는 기능, 도움이 필요한 부분

**규칙**

- 새 기능은 스크럼에서 제안하고, 팀이 동의하거나 제안자에게 맡긴다. 다음 날 "됐다 / 안 돼서 뺐다"를 보고한다.
- 오후 정리 시간에 "혼자 벅차다"는 부분이 나오면 다음 날 다른 팀원을 붙인다.
- PR은 작성자가 아닌 팀원 1명이 리뷰한다.
- 자기 기능의 핵심 결정 3가지를 AI 없이 설명할 수 있어야 PR을 합친다.
- 스크럼 마스터는 주 단위로 돌아가며 맡는다(첫 주 재웅). 진행만 맡고, 회의 안에서는 모두 동등하게 의견을 낸다.
- 회의 녹음은 돌아가면서 맡는다(받아쓰기 도구 사용 한도 때문).

## 오후 추가 논의 (10/30)

**정해진 것**

- **지영:** 예약 코어 담당에 동의. 예약 규칙 v2를 문서로 먼저 정리하고 구현한다. 요구사항 명세·배포 쪽도 같이 챙긴다는 말이 있었음 (누구 말인지 확인 필요)
- **재웅:** 인프라 담당 유지. 지영님의 예약 규칙을 받아 배포까지 연결한다. 각자 만든 뒤 나중에 합친다.
- **영준:** MCP·비서는 무조건 넣되, 예약 시스템이 제대로 돌아간 뒤에 붙인다. 기능 추가는 그때 다 같이 한다.
- **수연 + 영준 (센서):** Jetson은 쓰지 않고 브레드보드 + ESP32로 만든다. 그래서 회로도를 그려야 한다. 여러 방을 동시에 테스트하려면 ESP32가 여러 개 필요한데, 키트 6개 중 ESP32는 1개뿐이다.
- **스크럼 슬라이드:** 디자인 양식은 따로 정하지 않는다. 내용 4장 구조만 지킨다. 매일 화면을 연결해 다 같이 발표한다.
- **개인정보 처리 방침:** Claude가 초안을 쓴다.

**골라야 할 것: 자정을 넘는 예약**

지금 만든 방식은 23:30에 예약하면 그날 30분만 되고 다음 날로 넘어가지 못한다. 그런데 7일 사전 예약의 마지막 날 밤에 예약하면 끝나는 시각이 8일째가 되어 규칙과 부딪힌다.

| 안 | 규칙 | 장점 | 단점 |
| --- | --- | --- | --- |
| A. 넘기기 허용 (Claude 추천) | 시작 시각만 7일 안이면 된다. 23:00–01:00도 가능 | 시험기간 밤샘 이용에 맞다. "하루 1건"이 아니라 "끝나지 않은 1건" 규칙이라 날짜 경계로 깨지는 규칙이 없다. 시간 겹침 제약(tstzrange)도 자정을 그대로 처리한다 | 날짜별 시간표 화면에서 다음 날 앞부분에도 예약이 보여야 한다 |
| B. 넘기기 금지 | 끝나는 시각은 그날 24:00까지 | 화면·조회가 단순하다 | 23시 넘어 예약하는 사람은 00:00에 다시 예약해야 한다. 24시간 개방과 안 맞는다 |

A를 고르면 "7일" 검사는 시작 시각에만 하고, 날짜 계산은 서울 시간(Asia/Seoul) 기준으로 한다. 서버 시간대가 UTC면 오전 9시 전 예약이 하루 밀리는 버그가 생기기 쉽다.

**MCP 메모:** "내 수업 끝나는 시간 찾기 → 그 뒤 빈방 찾기 → 예약"처럼 도구를 여러 번 이어 부르는 것은 모델이 도구를 하나만 지원해서가 아니라, 에이전트가 "도구 결과를 모델에 돌려주고 다시 물어보는" 반복을 해야 된다. Gemini는 여러 번 도구 호출을 지원하고, Ollama도 도구 호출을 지원하는 모델이면 가능하다. 다만 작은 로컬 모델은 도구를 여러 번 이어 부르는 정확도가 낮을 수 있다 (확인 필요).
