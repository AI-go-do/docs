## 1. 왜 만드나

IT융합대학 M-space는 학생들이 회의와 스터디를 하는 방이다. 지금은 이렇게 쓴다.

> 교학팀에서 명부 작성 → 학생증 맡김 → 열쇠 받음 → 사용 → 열쇠 반납

이 방식은 **사람(교학팀)이 있어야만** 돌아간다. 그래서 세 가지 문제가 생긴다.

| 문제 | 실제로 겪는 일 |
|---|---|
| 관리가 끊긴다 | 교학팀은 18시에 퇴근한다. 시험 기간에는 24시간 열어 두지만 관리하는 사람이 없다 |
| 비었는지 모른다 | 방이 비었는지 직접 가 봐야 안다. 설문에서 가장 큰 불편 |
| 반납·신분증이 번거롭다 | 학과실이 닫히면 열쇠를 반납할 수 없다. 매번 학번을 적고, 학생증을 맡기는 게 불안하다 |

학생 설문(2026-10, 응답 약 6명, 추가 수집 중)에서 **열쇠 없이 예약만으로 이용하는 데 약 83%가 찬성**했다.

**그래서 우리가 만드는 것**: 사람이 없어도 "누가, 언제, 어느 방을 쓰는지"를 시스템이 기록하고 지키며, **예약만으로 문을 여는** M-space 예약·출입 시스템.

## 2. 어떻게 만드나

### 2.1 원칙

| 원칙 | 뜻 | 이렇게 한다 |
|---|---|---|
| 사람 대신 규칙이 지킨다 | 관리자가 없어도 규칙이 깨지지 않아야 한다 | 겹침 금지·1인 1건(대표자·참여자)·2시간 같은 규칙은 **DB 제약**으로 막는다. 동시 요청 100건에서 중복 0건 |
| 작게 만들고 바로 배포한다 | 다 만든 뒤 배포하지 않는다 | 첫날 빈 화면을 배포하고, 기능 하나를 붙일 때마다 폰으로 확인한다 |
| 갈아 끼울 수 있게 만든다 | 학교가 도입하면 실제 장비로 바꿀 수 있어야 한다 | 메일 인증 ↔ 학교 DB, 키패드 ↔ 실제 도어락, Gemini ↔ Ollama를 **인터페이스(포트) 뒤**에 둔다 |
| 사진·영상 남기지 않기 | 개인정보를 남기지 않는다 | 재실은 PIR·조도·CO2 센서로 판단한다(레이더 센서는 8차 회의에서 환불하기로 함). 방 카메라는 퇴실 뒤 정리 확인(FR-DEV-105)에만 쓰고, 장치 안에서 사람 수·물건 이름만 뽑고 화면은 바로 버린다. 사진·영상은 저장·전송하지 않는다(11/6 지영, Q-17) |
| AI는 붙이기 쉽게 | 나중에 비서가 예약을 대신 해 줄 수 있어야 한다 | 모든 기능을 API로 열고 자동 문서(OpenAPI)를 만든다. 비서는 이 API를 MCP 도구로 쓴다 |

- 점선은 나중 버전에 붙는 부분이다.

## 3. 버전별 범위

| 버전 | 한 줄 | 들어가는 것 |
|---|---|---|
| **v0.1** | 예약 한 바퀴 | 배포 파이프라인, 학교 메일 로그인, 방 목록, 예약(겹침·1인 1건·2시간·30분·7일), 참여자·방별 인원, 내 예약, 시작 전 취소, 6자리 번호 → 키패드 체크인, 퇴실 |

**하지 않는 것**
- 카메라 사진·영상 저장·전송, 얼굴 인식. 방 카메라는 정리 확인(FR-DEV-105)에 글자만 보낸다(11/6 지영). 카메라 인원 세기로 재실을 판단할지는 Q-17
- 키박스
- 학교 학사 DB 직접 연동 (인터페이스만)
- 학과 공지·휴강 수집 (8차 회의: 범위는 M-SPACE 안. 학생이 직접 넣는 내 시간표 FR-AGT-102a~는 유지)
- 실제 도어락 (어댑터 설계만)

**입실 방식 (8차 회의, 11/6)**: 시험용 방 **1실**에서 키패드 → NFC → QR 차례로 시도한다. 시연은 QR 입실(+ 카메라 인원 세기는 Q-17 결정에 따름)이고, 키패드는 "1차 시도"로 발표 슬라이드에 남긴다. 방식별 API 모양은 Q-16.

### 3.1 이용 수칙

예약할 때 동의를 받고, 위반은 신고(FR-RPT-101)와 관리자 판정(FR-RPT-103)으로 처리한다. 비서가 답하는 이용 규칙(Q-10 ③)에도 이 표가 들어간다.

| 구분 | 수칙 | 어기면 |
|---|---|---|
| 소음 | 회의·대화는 괜찮다. 옆 방에 들릴 만큼 떠들거나 장난치지 않는다 | 신고가 사실로 판정되면 경고. 심하거나 반복되면 이용 정지(퇴출) |
| 음식 | **음식물 반입 금지.** 먹을 것과 마실 것(음료 포함) 모두 가져올 수 없다 | 신고가 사실로 판정되면 경고. 기기·비품이 고장 나면 **배상을 요구**한다 |
| 정리 | 퇴실 전에 쓰레기를 버리고 자리를 정리한다 | 다음 사람이 어질러짐을 신고하고 사실로 판정되면 경고·이용 제한 등 불리하게 처리 |
| 노쇼 | 시작 15분 안에 키패드로 입실한다(즉시 시작은 10분) | 예약이 자동으로 풀린다(FR-RSV-102). **30일 안에 2번이면 14일 이용 정지**(대표자·참여자 모두, FR-RSV-106) |
| 자리 비움 | 짐만 두고 자리를 맡아 두지 않는다. 사용 중에 오래 비우지 않는다 | 센서가 10분 비어 있음을 보면 "5분 안에 돌아와 주세요" 알림, 15분이면 자동 퇴실(FR-DEV-103). **30일 안에 3번이면 노쇼 1번**으로 센다 |
| 증빙 | 체크인·퇴실 때 방 사진을 찍어 두기를 권한다(선택) | 사진이 없으면 분쟁 때 내가 정리했다는 증빙이 없어 불리할 수 있다 |
| 문 | 나갈 때 문이 닫혔는지 확인한다. 문을 괴어 두거나 번호를 예약자 밖 사람에게 알려 주지 않는다 | 무단 사용이 확인되면 그 예약 대표자에게 경고 |
| 소지품 | 퇴실 전에 챙긴다. 잠깐 나갈 때도 귀중품은 들고 나간다 | 예약이 끝나 문이 잠기면 다시 예약해야 들어갈 수 있다(3.2) |

**제재 단계** (경고·정지는 11/6 지영 확정. 심한 소음·고의 파손 즉시 정지와 배상은 제안, 교학팀 확인 필요)

| 단계 | 조건 | 조치 |
|---|---|---|
| 경고 (**확정**, 11/6 지영) | 신고가 사실로 판정 1회 | 그 방 **직전 이용 예약의 대표자**에게 알림으로 경고, 기록에 남김(FR-RPT-104) |
| 이용 정지 (**확정**, 11/6 지영) | 30일 안에 경고 3회 | 3번째 경고 때부터 14일 동안 예약·연장 불가. 정지가 걸리면 그 전 경고는 다시 세지 않음 |
| 즉시 정지 (제안) | 심한 소음·고의 파손 | 14일 이용 정지 (아직 만들지 않음) |
| 신고 정지 (**확정**, 11/6 지영) | 30일 안에 허위 신고 판정 3회 | 14일 동안 신고 불가(예약은 됨). 위반 경고와 따로 셈(FR-RPT-103) |
| 노쇼 정지 (**확정**, 11/4 지영) | 30일 안에 노쇼 2회(대표자 기록. 자리 비움 3번 = 노쇼 1번) | 2번째 노쇼가 처리된 때부터 14일 동안 대표자·참여자 모두 예약 불가. 정지가 끝나면 횟수는 처음부터(FR-RSV-106) |
| 배상 | 기기·비품 고장 | 관리자가 수리비를 따로 청구(시스템 밖에서 처리, 기록만 남김) |

### 3.2 이어 쓰기 · 퇴실 · 문 잠김 (11/3 회의)

키패드 입실에서 "안에 있는데 새 번호를 어떻게 넣나", "퇴실해야 문이 잠기나", "갇히지 않나"를 정리한 것이다. 문 하드웨어에 대한 내용은 **가정**이고 IoT 담당 확인이 필요하다(Q-14).

**전제 (가정, 확인 필요)**

| 항목 | 가정 | 근거 |
|---|---|---|
| 잠금 | 문은 닫히면 저절로 잠긴다(자동 잠금 도어락). 바깥에서는 번호로만 연다 | 일반 디지털 도어락 동작. 시연은 키패드 모형 |
| 안쪽 열기 | 안에서는 번호 없이 손잡이·버튼으로 **언제나** 열린다. 서버·와이파이·전원이 죽어도 열린다 | 갇힘 방지(피난). 장치 요구사항으로 고정한다(NFR-ACC-001) |
| 퇴실과 잠금 | 퇴실은 문을 잠그지 않는다. 퇴실은 **번호를 끄는 것**이다. 잠그는 것은 문이 닫힐 때 도어락이 한다 | FR-ACC-001: 서버는 "열어도 된다"만 답한다 |

**시나리오별 정리**

| # | 상황 | 생기는 문제 | 정한 동작 |
|---|---|---|---|
| S-1 | 13:00–14:00 사용 중, 13:50에 14:00–15:00을 이어 잡으려 함 | 대표자 동시 1건이라 지금 예약이 끝나기 전에는 새 예약이 거절된다(`OWNER_HAS_ACTIVE_RESERVATION`) | 사용 중 카드의 **"연장하기"**(FR-RSV-105, Q-12). 퇴실과 새 예약을 한 번에 처리해, 새 예약이 실패하면 지금 예약이 그대로 남는다. 그 전까지는 먼저 퇴실하고 새로 잡는다(FR-RSV-104). 이 경우 그 사이 다른 팀이 먼저 잡을 수 있다 |
| S-2 | 이어 잡은 새 예약의 번호를 받았지만 방 **안**에 있음 | 키패드는 바깥에 있다. 체크인을 안 하면 새 예약이 15분 뒤 노쇼로 풀려, 사람이 안에 있는데 다른 팀이 예약할 수 있다 | "연장하기"로 잡은 예약은 처음부터 사용 중이라 키패드가 필요 없다. 따로 잡은 새 예약은 바깥 키패드에 새 번호를 넣고, 잊으면 노쇼 5분 전 알림(FR-NTF-104)이 간다 |
| S-3 | 안에 가만히 있는데 문이 닫혀 잠김 | 갇힘 걱정 | 안쪽은 언제나 열린다(전제). 잠김은 바깥에서 들어오는 것만 막는다 |
| S-4 | 일찍 나가며 퇴실을 안 누름(사진도 귀찮아서 건너뜀) | 종료 시각까지 방이 묶이고 번호도 살아 있다 | 종료 시각에 자동 퇴실(FR-RSV-101). 센서가 10분 비어 있음을 보면 "5분 안에 돌아와 주세요" 알림, 15분이면 자리 비움으로 자동 퇴실(FR-DEV-103). 사진은 선택이고 안 찍으면 증빙이 없을 뿐이다 |
| S-5 | 잠깐 나갔다 오니 예약이 끝나 문이 잠김. 소지품이 안에 있음 | 끝난 예약의 번호는 무효라 못 들어간다 | **다음 예약이 없으면** 지금 바로 다시 예약해 새 번호로 들어간다. 단 연장까지 쓴 직후 30분 안이면 연속 사용 제한(FR-RSV-105)에 걸린다. 다음 팀이 쓰고 있으면 노크해서 부탁한다. 둘 다 안 되면 교학팀 |
| S-6 | 퇴실 후 번호를 다시 누름 | 끝난 예약 번호로 문이 열리면 무단 사용 | 퇴실·자동 퇴실·취소·노쇼가 되는 순간 번호는 무효(FR-ACC-001) |

## 4. 용어와 예약 상태

| 용어 | 뜻 |
|---|---|
| 방 | 창작실 1–5(현장 배치도 표기). 문서의 "N번 방"은 "창작실 N"과 같다. 방마다 최소·최대 인원이 있다. 옆의 3D프린터 공작실은 예약 대상이 아니다 |
| 예약 | 대표자가 한 방을 시작–종료 시각 동안 쓰겠다는 기록. 참여자 목록을 가진다 |
| 대표자 | 예약을 만든 사람. 참여자 목록에도 들어간다 |
| 참여자 | 예약에 함께 들어간 회원(대표자 포함). 대표자든 참여자든 끝나지 않은 예약은 동시에 1건만(11/5) |
| 끝나지 않은 예약 | 상태가 `BOOKED`(예약됨) 또는 `IN_USE`(사용 중)인 예약 |
| 체크인 | 키패드에 번호를 입력해 입실한 것 |
| 퇴실 | 사용을 마친 것. 버튼(즉시) 또는 종료 시각(자동). 퇴실하면 방이 바로 빈다 |
| 취소 | 시작 전에 대표자가 예약을 없애는 것. 즉시 시작은 누른 뒤 5분 안, 입실 전까지(11/6) |
| 노쇼 | 정한 시간 안에 체크인하지 않은 것. 방이 풀린다 |
| 자리 비움 | 체크인한 뒤 재실 센서가 15분 동안 아무도 없다고 본 것. 자동 퇴실되고 방이 풀린다. 노쇼(한 번도 안 옴)와 다르게 센다 |
| 미리 예약 | 미래 시각을 잡는 예약 |
| 즉시 시작 | 지금 빈 방을 누른 시각부터 쓰는 예약 (v0.2) |
| 시간 구간 | `[시작, 종료)`. 10:00–11:00 뒤의 11:00–12:00은 겹치지 않는다 |

```mermaid
stateDiagram-v2
    [*] --> BOOKED: 예약
    BOOKED --> CANCELED: 시작 전 취소 (즉시 시작은 누른 뒤 5분 안)
    BOOKED --> IN_USE: 키패드 체크인
    BOOKED --> NO_SHOW: 체크인 없음 (v0.2)
    IN_USE --> CHECKED_OUT: 퇴실 버튼
    IN_USE --> AUTO_CHECKED_OUT: 종료 시각 (v0.2)
    IN_USE --> AWAY_RELEASED: 15분 비어 있음 (v0.2)
```

- `BOOKED`·`IN_USE`를 벗어나는 순간 겹침·대표자 제약에서 빠지므로 방과 대표자가 바로 풀린다.
- 상태 이름은 제안이다. `schema-v2.sql`에 다른 이름이 있으면 그쪽을 따른다.

### FR-AUTH-001 학교 메일 인증 가입·로그인

- **설명**: 학생은 학교 메일로 받은 인증 번호로 가입·로그인한다. 인증을 마친 회원만 예약하거나 참여자로 추가될 수 있다.
- **규칙**
  - `@chosun.ac.kr` 주소만 받는다.
  - 인증 번호는 6자리, 10분 유효. 5번 틀리면 다시 받아야 한다. 같은 주소로 1분에 1번만 보낸다.
  - 처음 인증하면 이름과 학번을 받아 회원을 만든다. 학번은 회원마다 하나.
  - 로그인하면 JWT(액세스 토큰, 1시간)를 준다. 토큰에 권한 범위(scope)를 둔다. 개인정보는 넣지 않는다.
  - 본인 확인은 `IdentityVerifier` 뒤에 둔다. v0.1은 학교 메일 어댑터 하나. 학교 DB 연동은 인터페이스만.
  - 메일은 `NotificationChannel`(메일) 어댑터로 보낸다. 로컬·테스트에서는 로그에 번호를 찍는다.
- **수용 기준**
  - [ ] 조건: 가입 이력 없음 / 행동: `a@chosun.ac.kr`로 번호 요청 → 번호·이름·학번 입력 / 결과: 회원 1명 생성, 토큰 발급
  - [ ] 조건: 이미 가입 / 행동: 같은 주소로 다시 인증 / 결과: 같은 회원으로 로그인
  - [ ] 조건: — / 행동: `a@gmail.com`으로 요청 / 결과: `400` "학교 메일만 사용할 수 있습니다"
  - [ ] 조건: 번호 발급 후 11분 / 행동: 그 번호 입력 / 결과: `400` (만료)
  - [ ] 조건: 다른 회원이 학번 `20231234` 사용 중 / 행동: 같은 학번으로 가입 / 결과: `409`
- **관련**: FR-RSV-004, NFR-COM-003, FR-AUTH-002

### FR-AUTH-002 자동 로그인 · 로그아웃

- **설명**: 학생이 앱을 열 때마다 메일 인증을 다시 하지 않도록, 한 번 로그인하면 쓰는 동안 로그인이 유지된다.
- **규칙**
  - 로그인하면 액세스 토큰(1시간)과 refresh 토큰(14일)을 함께 준다.
  - 액세스 토큰이 끝나면 화면이 refresh 토큰으로 새 한 쌍을 받는다. 학생은 아무것도 하지 않는다.
  - refresh 토큰은 한 번 쓰면 새것으로 바뀐다(회전). 기한은 마지막으로 쓴 때부터 14일.
  - refresh 토큰은 DB에 해시로만 저장한다. 로그아웃하면 바로 끊는다.
  - 이미 쓴 refresh 토큰이 다시 오면 도난으로 보고 그 회원의 refresh 토큰을 모두 끊는다.
  - 기간(1시간·14일)은 설정값으로 둔다(`JWT_TTL`, `JWT_REFRESH_TTL`).
  - **같은 폰(브라우저)에서 마지막으로 쓴 지 14일이 안 됐으면 로그인 없이 바로 통과한다.** 다시 로그인하는 때는 처음 설치, 로그아웃, 다른 폰·브라우저, 브라우저 데이터 삭제, 14일 동안 안 씀뿐이다.
  - 앱을 열면 로그인 화면이 아니라 로딩 화면을 먼저 보여 준다. 그동안 ① 토큰이 있나 ② 액세스 토큰이 살아 있나(살아 있으면 바로 메인) ③ refresh로 새로 받기(성공하면 메인)를 확인하고, 실패했을 때만 로그인 화면을 보여 준다.
  - 화면: 마지막 학교 메일을 기억해 채우고, 번호칸에 `autocomplete="one-time-code"`. refresh는 동시에 한 번만 부른다.
  - 로그인이 끊겨도 예약·입실 번호는 그대로다. 다시 로그인하면 같은 회원으로 보인다.
  - **보안 체크 (운영 전 필수)**
    - 서버에는 `JWT_SECRET`(32바이트 이상)을 반드시 넣는다. 비우면 재시작할 때마다 토큰이 무효가 된다(로컬 전용).
    - 운영에서는 `MSPACE_DEV_HEADER=false`. 비서도 `X-User-Id`를 넘기지 않고 `Authorization`만 넘긴다.
    - nginx에서 `/api/auth/` 요청 횟수를 제한한다(인증번호·refresh 막 찌르기 방지).
    - 토큰은 HTTPS로만 오간다(학교 nginx HTTPS). 로그에 토큰·인증번호 원문을 남기지 않는다. 운영에서는 `MAIL_ENABLED=true`(false면 인증번호가 서버 로그에 찍힘).
    - 화면은 토큰을 다른 사이트 스크립트가 읽지 못하게 한다(외부 스크립트 최소화). 필요하면 refresh 토큰만 `HttpOnly` 쿠키로 옮긴다.
  - 게이트웨이(nginx)는 `/api/agent/`로 넘기기 전에 `auth_request`로 core `GET /api/auth/check`를 불러 토큰을 확인한다. 가짜 토큰으로 비서가 Gemini 무료 한도를 쓰지 않게 하기 위해서다. core는 토큰이 맞으면 `204`, 아니면 `401`.
- **수용 기준**
  - [ ] 조건: 가짜 토큰 / 행동: `POST /api/agent/chat` / 결과: 게이트웨이에서 `401`, 비서 서버까지 가지 않음
  - [ ] 조건: 로그인 후 2시간 / 행동: refresh 토큰으로 요청 / 결과: `200`, 새 액세스·refresh 토큰. 받은 refresh 토큰은 다시 쓰면 `401`
  - [ ] 조건: 13일마다 refresh / 행동: 3번 반복 / 결과: 계속 `200` (기한이 이어짐)
  - [ ] 조건: 14일 동안 안 씀 / 행동: refresh / 결과: `401` `REFRESH_TOKEN_INVALID` → 로그인 화면

### FR-RSV-003 회원당 끝나지 않은 예약 1건 (대표자·참여자 모두)

- **설명**: 미래 예약을 쌓아 방을 독점하지 못하게, 한 회원은 대표자든 참여자든 끝나지 않은 예약(`BOOKED`·`IN_USE`)에 동시에 1건만 들어간다. 하루 횟수 한도는 없다. (11/5 지영 결정: 원래는 대표자만 1건이었으나, 참여자로 예약이 있는데 대표자로 또 잡히는 것을 막는다)
- **규칙**
  - DB 부분 유니크 인덱스 두 개로 막는다: 대표자는 `one_active_per_owner`(예약 표), 참여자(대표자 포함)는 `one_active_per_member`(참여자 표, `active`인 줄만).
  - 내가 대표자로 걸리면 `409 OWNER_HAS_ACTIVE_RESERVATION`, 넣으려는 참여자 중 누가 걸리면 `409 PARTICIPANT_HAS_ACTIVE_RESERVATION`(누구인지는 알려 주지 않는다).
  - 퇴실·취소·노쇼가 되는 순간 다음 예약을 할 수 있다. 연장하기(FR-RSV-105)는 지금 예약을 먼저 퇴실하고 새 예약을 넣으므로 그대로 된다.
  - 이 때문에 이미 다른 예약이 있는 친구는 참여자로 넣을 수 없다.
- **수용 기준**
  - [ ] 조건: 내 예약 내일 14:00 `BOOKED` / 행동: 모레 예약 / 결과: `409` "끝나지 않은 예약이 이미 있습니다"
  - [ ] 조건: 끝나지 않은 예약 없음 / 행동: 같은 대표자가 다른 방·시간으로 100건 동시 요청 / 결과: 1건만 `201`
  - [ ] 조건: 내 예약을 퇴실 / 행동: 새 예약 / 결과: `201`
  - [ ] 조건: 내가 참여자인 예약 오늘 15:00–17:00 `BOOKED` / 행동: 내가 대표자로 19:00–21:00 예약 / 결과: `409 OWNER_HAS_ACTIVE_RESERVATION`
  - [ ] 조건: 회원 A가 다른 예약에 참여자로 `BOOKED` / 행동: A를 참여자로 넣어 시간이 안 겹치는 예약 / 결과: `409 PARTICIPANT_HAS_ACTIVE_RESERVATION`
  - [ ] 조건: 끝나지 않은 예약 없는 회원 A / 행동: A를 넣은 서로 다른 팀 100건이 다른 방·시간으로 동시 요청 / 결과: 1건만 `201`
- **관련**: FR-RSV-005, FR-RSV-007, FR-RSV-008

### FR-RSV-004 참여자 추가 (친구 중에서)

- **설명**: 대표자는 **서로 수락한 친구** 중에서 참여자를 고른다(11/6 지영 결정). 모르는 학번을 넣어 그 사람을 동의 없이 예약에 묶지 못하게 한다.
- **규칙**
  - 친구: 학번으로 친구 요청 → 받은 사람이 수락하면 친구. 한 번 수락하면 삭제할 때까지 친구 창에 계속 남는다. 거절·요청 취소·친구 삭제 가능(삭제하면 양쪽에서 빠진다).
  - 예약 참여자는 대표자와 친구인 회원만. 한 명이라도 아니면 예약이 거절된다(`403 PARTICIPANT_NOT_FRIEND`, 누가 아닌지는 알려 주지 않음).
  - 친구를 삭제해도 이미 잡은 예약의 참여자는 그대로다.
  - 학교 메일 인증을 마친 회원만 검색·친구 요청·추가된다(DB 외래 키로 한 번 더 막음).
  - 검색 결과에는 이름 일부만 보인다(예: 홍*동).
  - 중복은 학번으로 판단한다. 같은 사람을 두 번 넣을 수 없다.
  - 대표자도 참여자 목록에 들어간다.
- **수용 기준**
  - [ ] 조건: 학번 `20231234` 회원 "홍길동" / 행동: 검색 / 결과: "홍*동" 1건
  - [ ] 조건: 가입 안 한 학번 / 행동: 검색 / 결과: 빈 결과, 추가 불가
  - [ ] 조건: — / 행동: 같은 학번을 두 번 넣고 예약 / 결과: `400`
  - [ ] 조건: 친구가 아닌(요청만 보낸 것 포함) 학번 / 행동: 참여자로 넣고 예약 / 결과: `403 PARTICIPANT_NOT_FRIEND`
  - [ ] 조건: A가 B에게 요청 / 행동: B가 수락 / 결과: 둘 다 친구 목록에 보이고, A가 B를 참여자로 넣어 예약 가능
  - [ ] 조건: 친구 / 행동: 한쪽이 삭제 / 결과: 양쪽 목록에서 빠짐, 이미 잡은 예약은 그대로
- **관련**: FR-AUTH-001, FR-RSV-005

### FR-RSV-005 방별 인원, 참여자 같은 시간 두 방 금지

- **설명**: 방마다 정한 인원 안에서만 예약하고, 한 사람이 같은 시간에 두 방에 들어갈 수 없다. 최소 인원이 있어 혼자 여러 번 잇는 "대리 연속 예약"도 줄어든다.

- **수용 기준**

  - [ ] 조건: 5번 방(5–8명) / 행동: 9명 / 결과: `400`
  - [ ] 조건: 회원 A가 1번 방 14:00–16:00 참여 / 행동: A를 넣어 2번 방 15:00–16:00 예약 / 결과: `409`
  - [ ] 조건: 같음 / 행동: A를 넣어 2번 방 16:00–17:00 / 결과: `409` (11/5부터 FR-RSV-003. A의 14:00–16:00 예약이 끝난 뒤에는 `201`)

### FR-RSV-007 시작 전 취소

- **설명**: 대표자는 시작 전에 예약을 취소할 수 있다. 시작 후에는 취소할 수 없다. 단 **즉시 시작(FR-RSV-103)은 누른 뒤 5분 안이고 아직 입실 전이면 취소할 수 있다**(11/6 팀 결정 "3–5분"). 즉시 시작은 누른 시각이 시작이라 예외가 없으면 잘못 눌렀을 때 노쇼(FR-RSV-106 벌칙)밖에 없기 때문이다.
- **규칙**
  - 대표자만, `BOOKED`이고 지금이 시작 전일 때만. 상태 `CANCELED`.
  - 즉시 시작은 `BOOKED`이고 지금이 **누른 시각 + 5분 전**일 때도 취소된다. 입실 마감(누른 뒤 10분)을 넘지 않는다. 길게 열면 방을 잡아 두고 안 쓰다 취소하는 데 쓰여서 짧게 둔다. 분은 설정값(`mspace.reservation.instant-cancel.minutes`, 3–5 사이로 조정, 0이면 끔).
  - 조건부 UPDATE(`WHERE status = 'BOOKED' AND (start_at > now() OR (즉시 시작 AND now() < start_at + 5분))`)로 한 번만 처리한다.
  - 내 예약 응답에 `cancelableUntil`(이 시각 전까지 취소 가능)을 주고, 화면은 이 값으로 취소 버튼을 보인다.
- **수용 기준**
  - [ ] 조건: 내 예약 내일 14:00 / 행동: 취소 / 결과: `200`, 같은 시간 다른 팀 예약 `201`, 나도 새 예약 `201`
  - [ ] 조건: 시작 시각이 지남 / 행동: 취소 / 결과: `409` "시작한 예약은 취소할 수 없습니다"
  - [ ] 조건: 참여자 / 행동: 취소 / 결과: `403`
  - [ ] 조건: 즉시 시작 3분 전, 입실 전 / 행동: 대표자 취소 / 결과: `200`, 노쇼로 세지 않음, 바로 새 예약 가능
  - [ ] 조건: 즉시 시작 6분 전, 입실 전 / 행동: 취소 / 결과: `409`
- **관련**: FR-RSV-003, FR-RSV-103, FR-RSV-106, FR-WEB-002

- **규칙**
  - 번호는 대표자만 받는다.
  - 번호는 시작 10분 전부터 종료 전까지만 유효하다. 단 아직 입실하지 않았으면 입실 마감(미리 예약은 시작 + 15분, 즉시 시작은 누른 뒤 10분)까지만 열린다. 마감이 지나면 노쇼 정리 전이라도 키패드가 거절한다(11/3 지영). 이미 입실한 사람은 종료 전까지 다시 열 수 있다. 같은 방의 끝나지 않은 예약끼리 번호가 겹치지 않는다.
  - 장치는 `POST /api/access/verify {eventId, roomId, deviceId, code}`만 부른다(`AccessDevice` 어댑터). 장치 토큰(`Authorization: Bearer`)은 사람 토큰과 따로 두고, 장치마다 따로 준다(4차 회의).
  - 같은 `eventId`가 두 번 오면 처음 판정을 그대로 돌려주고 다시 처리하지 않는다(3차 회의). `eventId`는 `방-bootId-순번`(예: `1-1000002-3`)이고, `bootId`는 장치가 켜질 때마다 1씩 올려 재부팅 뒤 순번이 겹치지 않게 한다(4차 회의).
  - 거절도 `200 {"result":"DENIED","reason":...}`로 답한다. 장치는 `result`만 보고 LED를 켠다. `401`은 장치 토큰 문제, `400`은 형식 문제다.
  - 맞으면 처음 한 번은 `BOOKED` → `IN_USE`(체크인), 이후에는 문만 연다.
  - `CHECKED_OUT`·`AUTO_CHECKED_OUT`·`AWAY_RELEASED`·`CANCELED`·`NO_SHOW`가 되는 순간 그 번호는 무효다. 종료 시각 전이라도 퇴실했으면 열리지 않는다.
  - 서버는 "열어도 된다"만 답하고, 잠금은 문이 닫힐 때 도어락이 한다. 퇴실 API는 문을 잠그지 않는다(3.2).
  - 5번 연속 틀리면 그 방 키패드를 1분 잠근다.
  - 실제 도어락은 같은 API를 부르는 다른 어댑터로 설명만 한다. NFC·QR은 8차 회의(11/6)로 시험용 방 1실에서 키패드 다음 차례로 시도한다(API 모양은 Q-16).
- **수용 기준**
  - [ ] 조건: 내 예약 14:00 시작, 지금 13:55 / 행동: 키패드에 번호 입력 / 결과: 열림, 상태 `IN_USE`
  - [ ] 조건: 지금 13:40 / 행동: 입력 / 결과: 거절 (아직 이름)
  - [ ] 조건: 다른 방 번호 / 행동: 입력 / 결과: 거절
  - [ ] 조건: 키패드 연결 전 / 행동: 웹 "입실" 버튼 / 결과: 같은 결과 (대체 시연)
  - [ ] 조건: 14:00–16:00 예약을 15:00에 퇴실 / 행동: 15:10에 같은 번호 입력 / 결과: 거절
- **관련**: FR-RSV-001, FR-RSV-008, NFR-ACC-001

### FR-WEB-001 예약 화면

- **설명**: 폰 브라우저에서 방·시간·참여자를 골라 예약한다.
- **규칙**
  - 흐름: 홈 배치도에서 방 누르기(FR-WEB-004) → 날짜 칩 7개(오늘부터 7일) → 시간 → 함께 쓸 사람 → (처음·수칙 변경 때만) 이용 수칙 동의 → 예약 → 입실 번호 화면(FR-WEB-005).
  - 시간은 하루 48칸(30분 칸, 6열 격자)을 **한 화면에** 보여 준다. 가로로 밀어 넘기지 않는다. 이미 예약된 칸·지난 칸은 고를 수 없게 흐리게 표시한다. 시작 칸과 끝 칸을 눌러 고르고, 최대 2시간(4칸)을 넘기면 고를 수 없다.
  - 함께 쓸 사람: **내 친구 안에서만** 학번·이름으로 골라 한 명씩 추가·삭제한다(FR-RSV-004, web #35). 친구가 아닌 학번을 치면 "친구가 아니라 넣을 수 없어요"와 그 자리 친구 요청 버튼을 보여 준다. 친구 화면은 마이 탭 아래 `/me/friends`. 지금 인원과 방의 인원 범위(예: 3–5명)를 함께 보여 준다. 같은 시간에 다른 방에 들어간 사람은 추가할 수 없다고 바로 알려 준다.
  - 서버 오류 메시지(`409` 등)를 그대로 보여 준다.
  - 예약(미리 예약·지금 바로 쓰기)이 성공하면 화면에 폭죽을 2.6초 띄우고 입실 번호 화면으로 간다(11/6 스크럼, web #31). 휴대폰 "동작 줄이기"를 켠 사람에게는 띄우지 않는다.
  - **처음 예약할 때와 수칙이 바뀌었을 때만** 이용 수칙(3.1) 동의 화면을 띄운다. 동의하면 다음부터는 묻지 않는다(회원에 동의한 수칙 버전을 저장).
  - 동의 화면은 노쇼 15분(강조), 소음, 음식물 반입 금지, 정리, 사진(선택)과 제재(30일 안 경고 3회 → 14일 정지)를 한 화면에 보여 주고, "동의합니다"를 체크해야 "동의하고 예약하기" 버튼이 켜진다.
- **수용 기준**
  - [ ] 폰(가로 360px)에서 가로 스크롤 없이 예약을 끝낸다.
  - [ ] 동의한 적 없는 회원은 동의 전까지 예약할 수 없다. 동의한 회원은 다시 묻지 않는다.
  - [ ] 인원 미달·겹침이면 이유가 화면에 보인다.
- **관련**: FR-ROOM-001, FR-RSV-001, FR-RSV-004, FR-RSV-005

### FR-WEB-002 내 예약 화면

- **설명**: 내 예약을 보고 취소·퇴실한다.
- **규칙**
  - 대표자 예약: 6자리 번호, 취소(시작 전)·퇴실(체크인 후) 버튼.
  - 참여자 예약: 보기만.
  - 사용 중인 예약은 맨 위 **사용 중 카드**로: 방, 끝나는 시각, 남은 시간(1초마다 줄어듦), 대표자 버튼 **퇴실하기 · 연장하기 · 아직 있어요**(FR-DEV-103). 참여자에게는 "퇴실·연장은 대표자가 해요"(web #29). 키패드·QR로 입실하면 입실 번호 화면이 "문이 열렸어요" 뒤 마이 탭으로 넘어오고 사용 중 카드가 맨 위에 있다(web #27·#49·#50).
  - 다가오는 예약은 누르면 상세 화면으로 간다. 상세에서 취소 → 확인 창 → "취소됐어요" 상태.
  - 퇴실 화면: 정리 체크 목록(쓰레기·자리·창문) → 퇴실 사진(선택, 건너뛰면 "증빙이 없어 불리할 수 있어요" 안내) → "퇴실하기" → 완료.
  - v0.3: 입실·퇴실 사진 칸(찍은 시각 표시, 예약 상세는 사용 중일 때·퇴실 화면은 정리 체크 아래. 앱이 900KB 아래 JPEG로 줄여 보냄, FR-RPT-102), "방에 문제가 있나요?" 버튼 4개 → 신고 화면(FR-RPT-101).
  - v0.2부터 사용 중 카드에 **"연장하기"** 버튼을 둔다(FR-RSV-105). 사용 중이고, 종료 10분 전부터이고, 다음 칸이 비어 있을 때만 보인다. 누르면 30분 단위로 최대 2시간을 고른다. 연장은 새 예약 1건으로 기록되고 **1회만** 된다. 연장한 예약에서는 버튼이 보이지 않는다.
  - 버튼은 "취소할까요?" / "조기 퇴실할까요?" 확인을 거친다. 처리 후 목록을 새로고침한다.
- **수용 기준**
  - [ ] 퇴실 → 상태가 "퇴실"로 바뀌고 버튼이 사라진다.
  - [ ] 빠르게 두 번 눌러도 오류 화면이 없다.
- **관련**: FR-RSV-006, FR-RSV-007, FR-RSV-008

### FR-WEB-004 홈 (배치도 + 오늘 방 현황)

- **설명**: 앱을 열면 실제 배치도 모양으로 방 5개와 오늘 하루 예약 상황을 한눈에 보고, 방을 누르면 바로 시간 고르기로 간다.
- **규칙**
  - 현장 배치도 순서대로 창작실 5 → 1을 세로로 놓고, 위에 3D프린터 공작실(예약 불가, 점선), 오른쪽에 복도·입구를 그린다.

  - 위쪽에 "지금 비어 있는 방 N개 중 M개", 알림 종(안 읽은 알림 점), "지금 바로 쓰기"(v0.2 FR-RSV-103)·"이용 규칙" 바로가기.
  - 방 줄을 누르면: 그 방이 **지금 비어 있고 지금 시작해 쓸 칸이 있으면 그 방이 골라진 지금 바로 쓰기**(FR-WEB-102), 아니면 그 방의 시간 고르기(FR-WEB-001)로 간다(11/6 스크럼 "즉시 시작을 기본값", web #32). 지금 바로 쓰기 화면 아래에 "나중에 쓸 거예요 · 시간 골라 예약하기" 줄을 둔다.
  - 오늘 내 예약이 있으면 아래 카드로 보여 주고, 누르면 입실 번호 화면으로 간다.
  - v0.1의 "비어 있음"은 예약 기준이다. 센서로 실제 재실을 보여 주는 것은 FR-DEV-102(v0.2).
  - 아래 탭: 홈 · 배치도 · **마이** · 비서. 마이(`/me`)는 내 정보(수칙 동의), 사용 중/다가오는 예약 1장, 내 예약 목록(`/me/reservations`)·내 시간표·친구·이용 규칙·(관리자)·로그아웃을 한 곳에 모은다(11/6 재웅, web #50). 처음엔 탭 이름이 "내 예약"이었다.
- **수용 기준**
  - [ ] 폰(가로 360px)에서 방 5개와 0–24시가 스크롤 없이 보인다.
  - [ ] 빈 방 줄을 누르면 그 방이 골라진 지금 바로 쓰기가, 사용 중인 방 줄을 누르면 그 방의 시간 고르기 화면이 열린다.
  - [ ] 내 예약 구간은 다른 예약과 다른 색으로 보인다.

### FR-WEB-005 예약 완료 · 입실 번호 화면

**NFR-COM-008 AI 확장성 5가지**
1. 기능은 core API로만 연다. OpenAPI 자동 문서가 MCP 도구의 근거가 된다. 비서는 DB에 직접 접근하지 않는다.
2. 기록에 `created_via`(WEB / AGENT / DEVICE)를 남긴다. 비서는 예약 만들기 요청에 `X-Created-Via: AGENT`를 붙이고, 없으면 WEB이다(권한이 아니라 건수 구분용, 권한은 4번). WEB/AGENT 건수는 관리자만 `GET /api/reservations/stats`로 본다(11/3, 영준 요청·지영 결정). 쓰는 사람은 관리자, 쓰임은 비서 작업 숫자(발표용)다. 관리자 화면(FR-WEB-101)에 붙일지는 아직 정하지 않았다. 수용 기준: 관리자가 아니면 `403 ADMIN_ONLY`, 로그인 안 하면 `401`.
3. 상태 변경은 도메인 이벤트로 낸다.
4. JWT scope로 비서 권한을 제한한다. **v0.3은 아직 안 함**: 비서는 학생 본인 토큰을 그대로 넘기고, 쓰기는 확인 카드 [확인]으로만 실행해 막는다. scope 제한은 v0.3 이후(11/5 재웅).
5. LLM은 `LlmClient` 뒤에 둔다.

**Q-01 제안 SQL** (PostgreSQL 16에서 확인)

```sql
ALTER TABLE reservation DROP CONSTRAINT valid_length;
ALTER TABLE reservation ADD CONSTRAINT valid_length CHECK (
  end_at > start_at
  AND extract(epoch FROM end_at)::int % 1800 = 0
  AND end_at <= to_timestamp(ceil(extract(epoch FROM start_at) / 1800) * 1800) + interval '2 hours');
```

| 예약 | 결과 |
|---|---|
| 14:17–16:30 (즉시 시작) | 통과 |
| 14:00–16:00 | 통과 |
| 23:00–01:00 (자정 넘김) | 통과 |
| 14:00–16:30 | 거절 |
| 14:17–17:00 | 거절 |
| 14:00–15:10 | 거절 |

- 끝은 정각·30분이고, 끝 ≤ (시작을 30분 칸으로 올린 시각 + 2시간)이면 통과한다.
- 미리 예약의 시작이 정각·30분인지는 서버가 확인한다.
